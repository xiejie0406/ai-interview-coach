## 1. 执行摘要

### 1.1 一句话结论

**[分析推断]** Aden 的真正竞品不是某一个“会点鼠标的 Agent”，而是四类能力的组合：模型级 Computer Use、通用任务 Agent、企业 RPA/APA 平台、开源浏览器/桌面执行框架。Aden 若只证明“能看屏幕并点击”，很难形成壁垒；更有价值的方向是把采购询价和客服回复做成可等待、可审批、可接管、可恢复、可审计的业务闭环。

### 1.2 本轮最重要的判断

| 编号 | 判断 | 类型 | 对 Aden 的直接含义 |
| --- | --- | --- | --- |
| 1 | Computer Use 已逐渐成为模型和自动化平台的公共能力 | [官方事实] + [分析推断] | 不把“自动点击”本身当核心差异化 |
| 2 | 企业厂商普遍采用“Agent 判断 + 确定性流程/RPA 执行”的混合路线 | [官方事实] | Planner、Policy、Executor 应分层，而不是让一个模型全权操作 |
| 3 | 长任务的核心是持久状态、外部等待、恢复和人工协作，不是更长的对话上下文 | [分析推断] | Task Run 与业务状态机应成为产品主对象 |
| 4 | API、官方连接器、DOM/选择器通常比纯视觉点击更稳定 | [官方事实] + [分析推断] | 建议形成 API → DOM/CDP/selector → visual fallback 的执行阶梯 |
| 5 | 模型自行判断“是否危险”不能成为唯一安全门 | [官方事实] + [分析推断] | 外发、下单、付款、删除、凭证等动作必须经过确定性策略门 |
| 6 | 1688 自动化存在明确的平台许可前置条件 | [官方事实] | 商业化前核验开放平台、智能服务市场、用户授权及数据用途 |
| 7 | “个人微信客户端自动读写”与“企业微信/微信客服官方接口”不是同一条路线 | [官方事实] + [待验证假设] | 将个人微信桌面控制列为 Go/No-Go 门禁，优先验证官方 API 路线 |
| 8 | 国内 RPA 已覆盖网页、桌面、ERP、微信和计划任务 | [官方事实] | Aden 必须以垂直业务对象、异步沟通和结果核验形成差异 |
| 9 | 生产可观测性需要记录计划、步骤、工具输入输出、截图、人工决定和业务结果 | [官方事实] + [分析推断] | 不能只有“实时看 Agent 操作”的视频流 |
| 10 | 成本应按成功询价、有效报价、解决会话等业务结果衡量 | [分析推断] | 不只比较模型 token 或单步点击价格 |

### 1.3 建议保留的产品命题

**[分析推断]** 当前 PRD 中值得继续验证的产品命题是：

1. 用统一 Task Run 承载浏览器、桌面、ERP、知识库、文件和通讯工具。
2. 为采购询价和客服分别建立独立业务状态机，而不是共用一条泛化聊天流程。
3. 把“等待外部回复”作为一等状态，允许任务跨小时或跨天暂停并恢复。
4. 将业务事实、执行证据和人工审批放在同一个工作台中。
5. 采用本地 Windows Runner 与云控制面组合，并保留专用机器或私有部署路径。

### 1.4 必须先验证的门禁

| 门禁 | 当前结论 | 未通过时的影响 |
| --- | --- | --- |
| 1688 授权路线 | [官方事实] 1688 法律声明限制未经许可的机器人、爬虫和自动化获取/使用站内内容；智能服务市场协议提供受控开发路线 | 不能把模拟浏览和聊天默认视为可商用能力 |
| 微信路线 | [官方事实] 腾讯政策入口可定位微信软件协议；[待验证假设] 未核验到允许第三方自动读写个人微信聊天的公开官方接口 | 个人微信闭环可能需要改为企业微信/微信客服，或缩减 MVP |
| ERP 接口 | [待验证假设] PRD 未证明目标 ERP 都有稳定、授权明确的读写 API | 无 API 时 GUI 操作成本、错误率和审计复杂度显著上升 |
| 运行环境 | [待验证假设] 尚未决定员工当前桌面还是专用 VM/机器池 | 直接影响安全、并发、凭证、接管和稳定性设计 |
| 业务成功标准 | [待验证假设] 尚未定义固定任务集、成功率、人工介入率和时延阈值 | 无法判断 Demo 是否达到可交付水平 |

## 2. PRD 目标与本轮决策问题

### 2.1 PRD 当前目标

**[官方事实：原始 PRD]** Aden 被定义为 `Windows 桌面端 + 云端服务` 的企业智能执行平台，不是单纯聊天助手。其 Tool 底座计划统一承载浏览器、桌面、微信、ERP、知识库和文件操作。

**[官方事实：原始 PRD]** MVP 希望跑通两条闭环：

| 业务闭环 | PRD 目标链路 | 关键业务结果 |
| --- | --- | --- |
| 采购询价 | 以 1688 为主进行搜索、筛选、联系供应商、等待回复、追问、提取报价、比价 | 获得结构化且可追溯的供应商报价 |
| 微信客服 | 识别联系人、映射 ERP 客户、查询订单/库存/物流、生成或发送回复、高风险转人工 | 给出基于业务事实的正确回复并保留证据 |

**[官方事实：原始 PRD]** PRD 已把任务状态机、外部等待、暂停/停止、人工审核、接管、恢复、截图、日志、权限与审计列为重要能力；高风险动作默认等待人工。

**[官方事实：原始 PRD]** MVP 明确不做大规模 Agent Marketplace、复杂低代码 RPA 设计器、手机端、大量通讯渠道、多 Agent 协作和复杂财务写操作。

### 2.2 本轮不做什么

1. 不把竞品功能直接抄成 Aden 需求。
2. 不在没有目标客户数据的情况下确定产品优先级。
3. 不把厂商宣传的“自愈”“高成功率”“企业级”当作已独立验证的结果。
4. 不评判任何自动化路线是否合法；只记录需由产品、商务、安全或法务进一步确认的许可事实。
5. 不在本轮决定模型、RPA 引擎或部署厂商。

### 2.3 需要通过调研回答的问题

1. 行业内把桌面执行拆成哪些层，谁负责规划、执行、安全、状态和审计？
2. 代表产品如何处理登录、凭证、人工确认、用户接管和外部等待？
3. GUI Agent 与传统 RPA/API 应如何组合？
4. 通用 Agent 与企业自动化平台的边界在哪里？
5. 哪些能力已是企业采购基线，哪些只是新近 Preview 或宣传能力？
6. Aden 在采购和客服场景中可建立什么垂直差异？
7. 哪些不确定性会直接改变 MVP 范围？

## 4. 市场分层与竞争结构

### 4.1 四层市场地图

| 市场层 | 代表产品 | 主要卖点 | 通常交给客户的责任 | 与 Aden 的关系 |
| --- | --- | --- | --- | --- |
| 模型级 Computer Use | Claude、Gemini、OpenAI 相关 API 能力 | 看截图、生成鼠标键盘或浏览器动作 | 运行环境、状态机、权限、恢复、审计、业务核验 | 可作为执行或推理能力，不是完整产品替代品 |
| 通用任务 Agent | ChatGPT Work、Manus | 自然语言委派、多步骤执行、浏览器/本机接管 | 深度业务规则、专属数据模型、行业许可、企业流程集成 | 直接对标入口体验与用户接管，不直接覆盖垂直闭环 |
| 企业 RPA/APA 平台 | Microsoft、UiPath、Automation Anywhere、影刀、来也、实在智能 | 编排、机器人、连接器、权限、部署、监控、人工任务 | 具体业务建模、实施配置、业务结果定义 | 对标治理、执行可靠性和企业采购门槛 |
| 开源执行框架 | Browser Use、UI-TARS | 快速搭建浏览器或 GUI Agent，可自托管和二次开发 | 几乎完整的生产工程与治理责任 | 可用于技术试验或执行层参考，不是开箱即用企业平台 |

### 4.2 价值链拆解

**[分析推断]** 一个完整企业桌面执行平台至少包含以下八层，竞品通常只覆盖其中一部分：

```text
业务目标与对象
  → 计划与任务分解
  → 风险与授权策略
  → 工具路由与确定性编排
  → API / Browser / Desktop / File / Message 执行
  → 结果观察与业务核验
  → 持久状态、等待、重试、补偿、人工协作
  → 日志、截图、追踪、成本、审计与运营
```

### 4.3 已形成的行业基线

**[官方事实] + [分析推断]** 多家企业平台已公开提供或强调以下能力，可视为 Aden 面向企业时需要解释的基线：

1. Web、Windows 桌面、API/连接器之间的混合执行。
2. 机器人、Agent 和人的统一编排。
3. 凭证管理、角色权限或运行环境隔离。
4. 对高风险动作的确认、升级或人工任务。
5. Step/Run 级日志、截图、Trace 或运行历史。
6. 长任务暂停、恢复、重试和队列。
7. 云端、VPC、私有部署或自带机器等至少一种企业部署路径。
8. 用量、步骤、机器人、席位或 Agent 维度的商业计费。

### 4.4 尚未成为稳定共识的能力

1. **[官方事实]** Gemini Computer Use 仍标记为 Preview。
2. **[官方事实]** Microsoft 的 Hosted Browser、Cloud PC pool 等运行方式存在 Preview 标识。
3. **[官方事实]** UI-TARS Desktop 文档将产品标为 Technical Preview。
4. **[分析推断]** “任意桌面应用长期无人值守且高成功率运行”尚不是公开证据充分的行业能力。
5. **[分析推断]** 完全依赖视觉模型自动判断安全、恢复和业务正确性，尚不能替代确定性治理。

### 4.5 与相邻产品品类的边界

**[分析推断]** Aden 的边界应按“主要操作对象、交付物和生产责任”判断，而不是看产品是否也使用 Agent：

| 品类 | 主要操作对象 | 典型交付物 | 强项 | 与 Aden 的边界 |
| --- | --- | --- | --- | --- |
| 传统 RPA | 已知页面、桌面控件、API 和固定流程 | 可重复执行的流程、Bot、运行记录 | 确定性、批量、连接器、调度和治理 | 是 Aden 的执行层/集成对象；Aden 不应在一期复制通用流程设计器 |
| 纯浏览器 Agent | 网站、标签页、DOM/CDP 或网页截图 | 完成一次网页任务、抽取结果 | 网页理解、探索和快速适配 | 可承担 1688 等 Web 步骤；不能单独覆盖 ERP、桌面、异步业务状态和完整审计 |
| IDE/编码 Agent | 代码仓库、编辑器、终端、测试和构建系统 | 代码变更、测试结果、补丁或开发文档 | 软件工程推理和代码工具链 | 不是直接竞品；即使两者都调用终端/MCP，Aden 的对象仍是业务任务、外部账号和真实业务副作用 |
| 通用桌面 Agent | 浏览器、本机文件、应用和终端 | 跨应用任务结果 | 自然语言委派、广覆盖和用户接管 | 是入口与交互体验对标；缺少采购/客服业务对象和行业授权并不等于 Aden 闭环 |
| 企业 APA/Agent 平台 | Agent、Robot、API、人和企业系统 | 受治理的端到端业务流程 | 编排、权限、审计、部署和运营 | 是最接近的平台级竞品；Aden 需以更轻、更垂直的业务闭环区分 |

**[分析推断]** 因此，Aden 不应泛化成“能帮用户做任何电脑任务”的 AI 助手，也不应变成写代码的 Agent。它应限定为：在批准的业务目标、账号、机器、数据和动作策略内，持续执行采购与客服任务，并对每个真实业务副作用负责。

## 5. 代表竞品详析

### 5.1 OpenAI：ChatGPT Work、Workspace Agents 与 Cloud Browser

#### 产品定位

**[官方事实]** ChatGPT Work 面向可委派的长时、多步骤工作，任务可在云端继续执行并交付成品。旧的 ChatGPT agent 入口已迁移到 Work，故本报告不把早期 Operator 或旧 Agent 当作独立现行产品。

**[官方事实]** Workspace Agents 提供模板/Builder、共享、定时、API 和 Slack 等使用方式；面向企业的产品页面同时强调角色权限、审批点、监控和审计。后者属于官方产品声明，本轮未做租户级实测。

#### 核心运行逻辑

1. 用户在 ChatGPT 中给出目标，由 Work 在云端拆解并运行多步骤任务。
2. 需要网站交互时可使用独立 Cloud Browser，并在后台继续。
3. 登录或敏感输入可由用户在安全输入模式下完成。
4. 关键动作可要求确认，用户可观察并接管浏览器。
5. Workspace Agent 将可复用指令、工具和入口包装为团队资产。

#### 安全、状态与治理

**[官方事实]** Cloud Browser 文档描述了用户接管、关键动作确认和网站访问权限。企业 Workspace Agent 页面描述 RBAC、审批与审计能力，但具体可配置粒度需结合实际租户版本验证。

**[分析推断]** OpenAI 路线的优势是自然语言入口、通用推理、云端后台执行和较低上手门槛；弱点是采购询价、ERP 映射、消息幂等及平台授权仍需要 Aden 自己建模。

#### 商业模式与边界

**[官方事实]** ChatGPT Business 公开价约为每用户每月 25 美元（年付口径），Enterprise 询价；Workspace Agent 还可能按 Enterprise rate card 中的 token/灵活用量计费。实际组合和地区可用性需商务核验。

**对 Aden 的启示：[分析推断]** 借鉴“任务委派 + 后台执行 + 随时接管”的交互，但首屏不宜复制为万能聊天框；Aden 应把 Task、Computer、Business Data 和 Approval 作为并列主对象。

主要来源：[ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)、[Using cloud browser in ChatGPT](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)、[Workspace Agents](https://help.openai.com/en/articles/20001143/)、[Workspace agents for business](https://openai.com/business/workspace-agents/)、[ChatGPT pricing](https://openai.com/chatgpt/pricing)。

### 5.2 Anthropic：Claude Computer Use API

#### 产品定位

**[官方事实]** Claude Computer Use 是模型工具能力，不是托管好的企业桌面执行平台。当前文档描述 `computer_toolset_20260801` 工具集及截图、鼠标、键盘等动作；客户应用负责真正执行每次工具调用，并把结果返回模型。

#### 核心运行逻辑

```text
客户程序提供截图
  → Claude 返回 computer tool action
  → 客户程序执行动作
  → 客户程序返回新截图/结果
  → Claude 判断继续、结束或报错
```

**[官方事实]** Anthropic 明确说明完整 agent loop、运行环境和恢复由集成方实现；Computer Use 不在 Claude Managed Agents 中直接提供。

#### 安全与性能边界

1. **[官方事实]** 官方建议使用专用 VM/容器、最小权限、域名 allowlist，并避免给模型不必要的敏感数据。
2. **[官方事实]** Tool combinations 文档指出 Computer Use 最通用但也最慢；纯网页任务应优先考虑 Browser Use。
3. **[官方事实]** Computer Use 按普通模型输入输出、工具和截图视觉输入消耗计费，并非完整平台订阅价。

### 5.5 UiPath：Agent Builder + Maestro + ScreenPlay + Robots

#### 产品定位

5. **[官方事实]** ScreenPlay 主张跨平台自然语言 UI 自动化，并与选择器 RPA/API 并用；其“自适应”效果属于官方产品主张，本轮未实测。

**[官方事实]** 公开定价页提供约 25 美元/月的 Basic 入口，企业 Agent、Maestro、治理和自托管主要需更高套餐或询价，不能用 Basic 价格代表完整 Aden 对标方案。

**对 Aden 的启示：[分析推断]** UiPath 对 Aden 的最大参考不是某个按钮，而是“业务流程持久化、Agent 与确定性执行分工、人工任务、Trace”四者的组合。

## 7. 行业主流思路、业务逻辑与产品机制

### 7.1 执行通道按确定性排序

**[官方事实]** Anthropic 明确建议网页内任务优先 Browser Use，Computer Use 作为更通用但更慢的方式；UiPath、Microsoft、来也等也将 API、流程、RPA 和 GUI 能力组合使用。

**[分析推断]** Aden 可采用以下执行优先级：

```text
1. 官方业务 API / ERP API / 官方通讯 API
2. 平台官方连接器或受授权 RPA 接口
3. Browser DOM / CDP / selector
4. Desktop accessibility / selector
5. 图像识别与坐标定位
6. 多模态视觉 Agent 兜底
7. 人工接管
```

这样做的原因不是追求技术保守，而是每下降一层，页面漂移、误点、观察缺失、重试重复和审计解释成本通常都会增加。

### 7.2 Planner、Policy 与 Executor 分离

**[分析推断]** 推荐将职责明确拆开：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Planner | 理解目标、拆解步骤、选择候选工具、提出风险提示 | 最终批准高风险动作、直接保管明文凭证 |
| Policy Engine | 根据动作、对象、数据、金额、收件人、授权范围确定允许/拒绝/审批 | 开放式业务推理 |
| Executor | 按结构化参数调用 API、浏览器、桌面、ERP、文件或消息工具 | 自行扩大权限或改变任务目标 |
| Observer/Verifier | 采集截图、DOM、返回值和业务数据，判断后置条件 | 仅凭“点击成功”宣告业务成功 |
| State Machine | 保存 Run、Step、等待、重试、人工任务和恢复点 | 把全部状态留在模型上下文中 |

#### 完整运行闭环

**[分析推断]** 生产链路必须形成可反复运行的闭环，而不是“模型生成一串点击后结束”：

```text
任务规划
  → 权限与策略确认
  → 选择执行通道并执行
  → 观察工具结果、页面状态和业务后置条件
  → 判断成功 / 纠错 / 降级 / 等待 / 人工接管
  → 保存检查点与业务状态
  → 生成证据和审计记录
  → 继续下一步或结束 Run
```

每一环都应有结构化输入输出。尤其要区分：

1. `tool_succeeded`：工具调用返回成功。
2. `ui_changed_as_expected`：页面或桌面进入预期状态。
3. `business_outcome_verified`：外部消息、ERP 数据或报价对象满足业务后置条件。

只有第三层成立，任务才可宣告业务完成；第一层或第二层失败时，应根据副作用风险决定重试、降级、恢复或人工处理。

### 7.3 持久状态机优于长对话

**[官方事实]** UiPath 等企业平台明确支持在人工或外部步骤暂停并恢复；Microsoft、OpenAI 等提供后台或异步运行形态。

**[分析推断]** Aden 的 Task Run 至少需要以下稳定状态：

```text
CREATED
  → PLANNING
  → READY
  → RUNNING
  → WAITING_EXTERNAL | WAITING_APPROVAL | WAITING_USER_INPUT
  → PAUSED | TAKEOVER
  → RUNNING
  → SUCCEEDED | PARTIALLY_SUCCEEDED | FAILED | CANCELLED
```

每次状态变化都应有：触发者、时间、前置状态、动作、证据、业务对象、恢复点和下一次唤醒条件。

### 7.4 采购询价应是业务状态机

**[分析推断]** 采购闭环不应只表现为“Agent 打开 1688 搜索”，建议把业务对象建模为：

```text
SourcingRequest
  ├─ requirement_spec
  ├─ supplier_candidates[]
  ├─ conversation_threads[]
  ├─ quotation_versions[]
  ├─ follow_up_deadlines[]
  ├─ comparison_snapshot
  └─ evidence_refs[]
```

建议状态：

```text
DRAFT → SEARCHING → CANDIDATES_READY → CONTACT_APPROVAL
→ CONTACTED → WAITING_REPLY → NEEDS_FOLLOW_UP
→ QUOTES_COLLECTED → NORMALIZATION_PENDING
→ COMPARISON_READY → HUMAN_DECISION → CLOSED
```

关键核验不是“消息发出”，而是：收件人正确、规格完整、发送未重复、供应商回复与会话匹配、价格/税/运/起订量/交期字段可追溯到原始证据。

### 7.5 客服回复也应是业务状态机

**[分析推断]** 客服闭环建议建模为：

```text
ServiceConversation
  ├─ channel_identity
  ├─ customer_match
  ├─ order_refs[]
  ├─ inventory_or_logistics_facts[]
  ├─ reply_draft
  ├─ risk_classification
  ├─ approval_or_escalation
  └─ outbound_message_receipt
```

建议状态：

```text
RECEIVED → IDENTITY_MATCHING → FACT_GATHERING
→ DRAFTING → POLICY_CHECK
→ AUTO_SEND | WAITING_APPROVAL | ESCALATED
→ DELIVERY_CONFIRMED → WAITING_CUSTOMER | RESOLVED
```

关键核验不是“生成了一段看起来合理的话”，而是客户映射正确、业务事实新鲜、承诺在授权范围、消息只发送一次、发送结果可追溯。

### 7.6 审批必须是结构化对象

**[官方事实]** OpenAI、Microsoft、UiPath 等产品均提供不同形式的确认、人工监督、升级或接管；Microsoft 明确提示概率触发不能作为 fail-safe。

**[分析推断]** Aden 不宜只弹出“是否允许继续”，审批对象至少应包含：

```json
{
  "action": "send_supplier_message",
  "risk_level": "high",
  "target": {
    "platform": "1688",
    "account": "masked-account",
    "recipient": "supplier-id"
  },
  "business_object": "sourcing-request-id",
  "payload_preview": "待发送内容",
  "data_classes": ["product_spec", "contact_info"],
  "policy_reasons": ["external_message", "first_contact"],
  "evidence_before": ["screenshot-ref", "quote-ref"],
  "expiry_at": "timestamp",
  "allowed_decisions": ["approve_once", "edit", "reject", "take_over"]
}
```

### 7.7 重试必须与幂等、Outbox 和补偿绑定

**[分析推断]** GUI Agent 失败后直接“再试一次”会产生重复询价、重复客服回复或重复写 ERP。建议：

1. 每个外部副作用动作生成业务幂等键。
2. 外发消息先进入 Outbox，审批和发送回执写入同一业务记录。
3. 重试前先查询后置条件，而不是盲目重复动作。
4. 无法确认是否成功时进入 `UNKNOWN_OUTCOME`，交给人工而不是继续发送。
5. 为可逆动作定义补偿，为不可逆动作定义停止和升级路径。

### 7.8 证据包而不是“看直播”

**[官方事实]** Microsoft Activity Map、UiPath Agent traces、Manus 操作日志和 UI-TARS 回放均说明运行证据是主流产品组成。

**[分析推断]** 每个 Run 的证据包应包含：

1. 原始目标和批准的计划版本。
2. 每个 Step 的工具、结构化输入、返回值和耗时。
3. 关键动作前后截图或 DOM 摘要。
4. 凭证引用而非明文凭证。
5. 模型、提示模板、策略版本和自动重试次数。
6. 所有外发内容、收件人、送达回执和幂等键。
7. 人工审批、编辑、接管、拒绝和恢复记录。
8. 最终业务对象及其事实来源。

### 7.9 验证与成本口径

**[分析推断]** 测试应分五层：工具契约测试、页面/选择器回归、Agent Eval、业务流程仿真、受控生产灰度。建议同时统计：

| 指标 | 定义示例 |
| --- | --- |
| 任务成功率 | 固定任务集中达到业务后置条件的比例 |
| 无人完成率 | 不需人工输入或接管即可完成的比例 |
| 错误外发率 | 错发、重复发、越权发占所有外发动作比例 |
| 恢复成功率 | 可恢复异常中自动或人工恢复成功比例 |
| 平均人工分钟 | 每个成功任务需要的审核和接管时间 |
| 有效报价成本 | 模型、浏览器、机器、人工和失败重试总成本 / 有效报价数 |
| 解决会话成本 | 全链路成本 / 符合解决标准的客服会话数 |
| P95 完成时延 | 从任务创建到业务完成的第 95 百分位时间，外部等待单独拆分 |

## 8. 安全、权限与平台边界

### 8.1 威胁面

| 威胁 | 典型场景 | 必要控制 |
| --- | --- | --- |
| Prompt injection | 网页、供应商消息或文件中包含诱导 Agent 改变目标的文字 | 不信任外部内容；系统目标与工具策略隔离；高风险动作确定性审批 |
| 过度授权 | Agent 获得整个桌面、全部文件、终端或多个账号 | 专用环境、最小权限、路径/域名/应用 allowlist、短期凭证 |
| 数据外泄 | 将 ERP 客户、报价、联系人或截图发送给不必要的模型/站点 | 数据分级、字段脱敏、目的限制、出站检查和日志留存策略 |
| 错误外发 | 回复发错客户、询价发错供应商或泄露其他客户信息 | 身份二次核验、收件人锁定、内容预览、审批和发送回执 |
| 重复副作用 | 重试导致重复消息、重复订单或重复写入 | 幂等键、Outbox、后置查询、`UNKNOWN_OUTCOME` 状态 |
| 凭证暴露 | 截图、模型上下文或日志中出现密码、验证码、Cookie | 凭证保险库、安全输入、日志掩码、截图敏感区域处理 |
| 接管竞态 | 人和 Agent 同时操作同一桌面或会话 | 明确控制权令牌，接管时立即冻结 Executor |
| 供应链风险 | 开源 Agent、浏览器扩展或依赖更新引入风险 | 版本固定、依赖审查、隔离运行、制品签名和变更回归 |

### 8.2 建议的动作风险分级

**[分析推断]** 以下是研究建议，不是已批准需求：

| 级别 | 动作示例 | 默认策略 |
| --- | --- | --- |
| L0 只读低风险 | 打开白名单页面、查 ERP 只读字段、读取授权文件 | 可自动执行，保留日志 |
| L1 可逆内部动作 | 创建草稿、保存内部备注、整理文件到临时区 | 可按策略预授权，支持撤销 |
| L2 外部沟通 | 首次联系供应商、客服回复、上传附件 | 内容与收件人检查；按模板/客户/时段决定逐次审批或预授权 |
| L3 高影响动作 | 下单、付款、改价格、删数据、执行脚本、扩大权限 | 必须确定性阻断并逐次人工批准；MVP 原则上不自动化 |

### 8.3 运行环境边界

**[官方事实]** Anthropic 建议专用 VM/容器和最小权限；Microsoft 建议专用机器并说明同机任务可能排队；Manus 和 OpenAI 提供各自隔离浏览器或授权范围机制。

**[分析推断]** Aden 优先考虑“一 Run 一隔离浏览器会话”与“专用 Windows Runner 队列”，而不是默认接管员工正在使用的桌面。员工桌面可作为有人值守模式，但需明确：

1. 哪个窗口和账号属于本 Run。
2. 接管发生时谁持有控制权。
3. 屏幕上其他应用和通知如何隔离。
4. 锁屏、休眠、多显示器、分辨率变化如何处理。
5. 登录态、Cookie 和本地文件何时销毁。

#### 本地、云端与混合执行取舍

| 模式 | 适合场景 | 优点 | 主要风险 | 凭据隔离要求 |
| --- | --- | --- | --- | --- |
| 本地执行 | 内网 ERP、本机应用、USB/证书、客户数据不可出域 | 接近现有业务环境、网络路径短 | 干扰员工桌面、机器漂移、运维分散 | 系统凭据保险库；按用户/任务授权；禁止模型直接读取明文；独立 Windows 账号或 Runner 服务身份 |
| 云端执行 | 公网网站、标准浏览器、可集中托管的账号 | 易扩容、易重置、会话隔离一致 | 数据出域、地区可用性、网站风控、云成本 | 每 Run 独立浏览器 Profile；短期凭证；域名 allowlist；任务结束销毁会话 |
| 混合执行 | 云端规划与控制，本地 Runner 执行 ERP/桌面动作 | 兼顾集中治理与本地系统接入 | 控制面与 Runner 断连、状态分叉、证据同步 | 云端只持凭据引用；本地解封短期凭据；双向认证；离线时冻结高风险动作；恢复后核对检查点 |

**[分析推断]** 对 PRD 的 Windows 桌面端 + 云服务形态，混合模式最贴近目标，但也是状态一致性和凭据治理最复杂的方案。PoC 必须验证断网、Runner 重启、接管和凭据过期，而不能只验证正常点击路径。

### 8.4 1688 自动化边界

**[官方事实]** [1688 网站法律声明](https://terms.alicdn.com/legal-agreement/terms/suit_bu1_b2b/suit_bu1_b2b201802011532_36855.html) 的 2026-01-16 版本限制未经许可通过机器人、爬虫、自动化程序、设备监视或模拟用户操作擅自获取、使用站内内容。

**[官方事实]** [1688 智能服务市场入驻协议](https://terms.alicdn.com/legal-agreement/terms/common_platform_service/20260127150801893/20260127150801893.html) 说明可通过开放平台和指定 RPA 编译后台开发授权智能服务，同时涉及入驻、审核、用户授权和数据用途限制。

**[分析推断]** 这两份材料共同说明：

1. “技术上能模拟浏览器”不等于“可直接商业化”。
2. Aden 应先核验开放平台/智能服务市场的正式接入路径、可调用能力和数据使用范围。
3. 如果搜索、聊天或报价抽取能力不在授权范围内，采购 MVP 必须改变技术路线或产品边界。
4. 法务结论、合同许可和账号授权应由相应负责人确认，本报告不作法律判断。

### 8.5 个人微信与企业微信必须拆开

#### 个人微信客户端

**[官方事实]** [腾讯政策入口](https://www.tencent.com/zh-cn/policies/) 提供微信软件许可及服务协议等政策链接。相关协议对非腾讯开发或授权的第三方软件、插件、外挂或系统登录/使用存在限制。

**[待验证假设]** 本轮未核验到允许第三方 Agent 自动读取、发送个人微信聊天的公开官方 API，也未完成目标使用方式的法律与账号安全评估。因此“控制个人微信客户端”必须是单独的 MVP Go/No-Go 门禁，不能因 RPA 厂商产品页出现“微信”二字就视为已经获准。

#### 企业微信 / 微信客服官方接口

**[待验证假设]** 企业微信公开开发体系存在客户联系、微信客服、智能机器人、会话内容存档等受控能力入口，但具体能力取决于企业认证、应用权限、客户授权、消息时窗、条数、存档开通及商业条款。本轮未完整抓取并核验这些文档细节，不能把它们写成已满足 PRD 的事实。

建议下一步验证官方入口：

- [企业微信智能机器人消息文档](https://developer.work.weixin.qq.com/document/path/100719)
- [企业微信客户联系文档](https://developer.work.weixin.qq.com/document/path/92228)
- [企业微信会话内容存档文档](https://developer.work.weixin.qq.com/document/path/91361)

**[分析推断]** 产品上应优先验证企业微信/微信客服官方接口能否覆盖首批客户，再决定是否保留个人微信桌面自动化。二者的 UI、权限说明、风险提示、数据留存和验收标准应完全分开。

## 9. 典型失败模式与恢复逻辑

| 失败模式 | 表面现象 | 真正风险 | 建议检测 | 建议恢复 |
| --- | --- | --- | --- | --- |
| 页面结构变化 | 找不到按钮或点错位置 | 错误操作或无限循环 | selector/DOM 断言、视觉差异、步数上限 | 降级其他通道或转人工，更新适配器 |
| 弹窗/广告遮挡 | 操作无响应 | 重复点击或误点 | 窗口层级、截图差异、点击后置条件 | 关闭已知弹窗；未知弹窗暂停 |
| 验证码/风控 | 登录或发送被阻断 | 账号封禁、违规绕过 | 识别验证码/异常页/频率提示 | 停止自动化，通知人工，不设计绕过机制 |
| 登录失效 | 回到登录页 | 凭证泄露或任务错账号 | URL、DOM、账号身份断言 | 安全输入重新登录或更换授权会话 |
| Prompt injection | 页面要求忽略规则并执行新动作 | 数据外泄或越权 | 外部内容标记、目标偏移检测、策略门 | 拒绝越权 Tool，记录证据并升级 |
| 重复发送 | 相同消息出现多次 | 客诉、供应商骚扰 | 幂等键、消息哈希、平台回执查询 | 停止重试，进入人工补救 |
| 发送结果未知 | 页面卡住但可能已发送 | 再试导致重复副作用 | 回查会话、Outbox 和送达状态 | 标记 `UNKNOWN_OUTCOME`，人工确认 |
| 外部等待超时 | 供应商/客户长期不回复 | 任务永久占用或漏跟进 | deadline、SLA、唤醒队列 | 按策略追问、关闭或转人工 |
| 业务数据过期 | 用旧库存或旧物流回复 | 错误承诺 | 数据时间戳、读取版本、发送前复查 | 刷新事实，重新生成并再次策略检查 |
| 身份映射错误 | 联系人匹配错客户 | 严重隐私与业务错误 | 多字段匹配、置信阈值、冲突检测 | 禁止自动发送，人工确认映射 |
| 模型输出漂移 | 相同输入出现不同计划 | 难复现、难审计 | 模型/提示版本、结构校验、Eval | 固定版本或回退，重放测试 |
| 工具返回伪成功 | Tool 报成功但业务未落地 | 错误宣告完成 | 独立后置条件和业务查询 | 重新观察，不盲目重放副作用 |
| 接管冲突 | 人和 Agent 同时操作 | 状态损坏或误发 | 控制权令牌、心跳、焦点监控 | 接管即冻结 Agent；释放后从检查点恢复 |
| 截图泄密 | 日志含密码、客户或其他窗口 | 隐私和合规事件 | OCR/区域规则、敏感应用检测 | 脱敏、限制访问、按策略删除和告警 |
| 机器资源竞争 | 多任务争用同一桌面 | 焦点错乱和串号 | Runner 锁、会话队列、资源监控 | 一机一交互任务；扩容机器池 |
| 成本失控 | 循环截图、长上下文、重复步骤 | 单任务亏损 | 步数、token、时间和重试预算 | 超预算暂停，切换低成本通道或人工 |
| 平台许可不满足 | 功能能跑但不允许商用 | 封号、下架、合同或合规风险 | 接入前许可清单、账号/应用授权审计 | 禁止上线；改走官方接口或缩范围 |

### 10.2 不宜照搬

1. **万能聊天首页**：对运营人员而言，任务、业务对象、异常和审批比聊天记录更重要。
2. **默认全盘、全终端权限**：便利不能替代最小权限和授权范围。
3. **纯像素执行**：应作为最后兜底，而不是主要执行通道。
4. **只靠模型触发审批**：概率判断不是确定性安全边界。
5. **首期复杂低代码设计器**：与 PRD 的 MVP 取舍冲突，也会把资源投入通用平台竞争。
6. **首期 Marketplace**：缺少稳定 Tool、治理和开发者生态时，市场并不能产生价值。
7. **宣传式自动自愈**：必须落到错误分类、检查点、幂等、补偿和人工队列。
8. **大型 RPA 的完整许可证/CoE 架构**：Aden 首期只需满足目标客户真实采购门槛。
9. **把开源 Demo 当企业平台**：运行成功不等于权限、审计、SLA 和可运营。
10. **把个人微信与企业微信混为一谈**：平台许可、身份、接口和风险完全不同。

## 11. 差异化机会

### 11.1 机会一：围绕业务结果，而不是点击能力

**[分析推断]** 将产品成功定义为“得到完整可比报价”或“基于正确业务事实解决会话”，而不是“Agent 成功完成 23 次点击”。这会自然要求 Aden 建立垂直数据对象、结果核验和证据引用。

### 11.2 机会二：异步多轮沟通状态机

**[分析推断]** 通用 Agent 擅长一次委派，传统 RPA 擅长确定性流程；供应商几小时后回复、客户再次追问、报价版本变化等跨时异步状态，可能成为 Aden 最有价值的专用能力。

### 11.3 机会三：业务事实、执行证据、审批联动

**[分析推断]** 审核人不应在聊天、ERP、截图和 Agent 日志之间来回切换。一个审批界面同时展示：客户/供应商身份、订单或询价事实、待发内容、风险原因、前后截图和历史决定，可显著降低人工审核成本。

### 11.4 机会四：授权优先的中国平台适配器

**[待验证假设]** 如果 Aden 能把 1688 开放平台/智能服务市场、企业微信/微信客服和常见 ERP 的正式授权路径产品化，可能比通用桌面模拟更有商业可信度。

### 11.5 机会五：行业字段模板和可比较报价

**[待验证假设]** 为服装、包装或其他首批行业预置规格字段、税运口径、MOQ、样品、交期、付款方式、供应商评分和 ERP 映射，可能构成比通用 RPA 更直接的用户价值。具体行业必须由首批客户决定。

### 11.6 机会六：轻量异常运营台

**[分析推断]** 相比先建设复杂流程设计器，优先建设“待审批、待补充、登录失效、验证码、结果未知、数据冲突、超时未回复”队列，更贴近真实生产运营。

### 11.7 机会七：本地 Runner + 云控制面 + 可选私有部署

**[待验证假设]** 该组合可能同时满足本地桌面/ERP 接入、云端编排和企业部署要求。但需用客户网络、数据出境、模型可用区、运维能力和成本验证，不能仅凭架构偏好决定。

## 12. 对首轮页面原型的研究输入

> 本节只提出原型验证方向，不代表页面范围已经批准。

### 12.1 建议验证的四个主对象

| 主对象 | 用户要回答的问题 | 原型需呈现的关键信息 |
| --- | --- | --- |
| Task | 现在有哪些任务，为什么停住？ | 目标、状态、业务对象、负责人、下一步、SLA、成本 |
| Computer | Agent 正在哪台机器/浏览器做什么？ | 会话画面、控制权、账号、应用、步骤、暂停/接管 |
| Business Data | Agent 的判断基于哪些事实？ | 询价、报价、供应商、客户、订单、库存、物流及来源 |
| Approval | 我具体在批准什么风险？ | 动作、对象、收件人、内容、数据、证据、策略原因、有效期 |

### 12.2 建议优先画的页面

1. 任务列表与异常队列。
2. Task Run 详情：计划、步骤、状态、等待、证据时间线。
3. Computer 观察与接管界面。
4. 结构化 Approval 审批页。
5. 采购询价工作台：候选供应商、会话、报价版本、比价。
6. 客服工作台：联系人映射、业务事实、回复草稿、风险和送达状态。
7. Tool、账号、机器与授权范围设置页。

### 12.3 原型要验证的关键交互

1. 一个任务等待供应商回复时，用户是否能看懂何时会再次唤醒。
2. 用户从自动执行切换到接管后，Agent 是否明确停止操作。
3. 审批人能否在 30 秒内判断收件人、内容和事实是否正确。
4. 发送结果未知时，界面是否阻止盲目重试。
5. 同一报价多轮变化时，是否能追溯字段的原始消息证据。
6. 客户身份匹配冲突时，界面是否强制进入人工确认。
7. 个人微信与企业微信路线是否在产品中明确区分，而不是只显示“微信”。

## 13. 下一轮需要讨论的问题

### 13.1 客户与场景

1. 首批客户是谁，属于哪个行业、规模和数字化水平？
2. 首个必须成功的采购品类是什么，规格字段是否稳定？
3. 客服会话量、峰值并发、平均响应时限和夜间值守要求是什么？
4. MVP 验收是一次 Demo，还是固定任务集上的统计成功率？

### 13.2 平台与授权

5. 1688 是否已有开放平台、智能服务市场或书面授权路径？
6. 客服是否必须使用个人微信，还是可切换企业微信/微信客服？
7. 企业微信目标能力需要哪些认证、权限、存档或商业开通？
8. 遇到验证码、账号风控或平台反自动化时，产品是否接受停止并转人工？

### 13.3 系统与数据

9. 目标 ERP 是什么，是否有稳定 API，哪些读取和写入动作一期允许？
10. Agent 运行在员工当前桌面、专用 PC、云 VM 还是客户私有机器池？
11. 截图、消息、日志和模型输入保存多久，谁可以查看？
12. 模型和云服务在目标地区的数据、网络、延迟和成本约束是什么？

### 13.4 权限与人工协作

13. 哪些外发消息必须逐次审批，哪些模板/客户/时段可预授权？
14. 审批超时后是自动取消、继续等待、转交还是升级？
15. 用户接管后如何恢复，是否需要重新核验页面和业务状态？
16. 重试产生重复询价或回复时，业务上允许怎样补偿？

### 13.5 商业模式

17. 按席位、Agent、Runner、Run、用量还是成功结果计费？
18. 客户更在意减少人工、缩短响应时间、提高报价覆盖还是可审计？
19. 是否接受一期只做 1688 授权路线 + 企业微信官方路线，暂缓个人微信？
20. Aden 是独立平台，还是作为现有 ERP/RPA 的业务层和控制面？

## 16. 本轮结论与下一阶段输入

本轮已经完成市场分层、11 个代表对象的公开资料分析、逐项矩阵、主流执行逻辑、安全边界、平台许可风险、失败模式和差异化机会梳理。

**[分析推断]** 下一阶段不宜立即把所有竞品能力合并成大而全的设计文档。更合理的顺序是：

1. 先回答第 13 节中的客户、1688、微信、ERP、运行环境和验收问题。
2. 选择采购或客服中的一条作为首个主闭环，另一条只保留必要共用底座。
3. 为选中的闭环确认业务对象、状态、动作风险和成功后置条件。
4. 再绘制 Task、Computer、Business Data、Approval 四类核心页面原型。
5. 用固定任务集做可点击原型评审与技术 Spike，之后再冻结设计文档范围。

当前最需用户参与的产品决定是：**一期是否接受只走 1688 正式授权路径和企业微信/微信客服官方能力，并把个人微信客户端自动化暂列为待验证范围。**

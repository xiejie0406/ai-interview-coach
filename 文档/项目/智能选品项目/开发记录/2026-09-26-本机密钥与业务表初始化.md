## 范围与预检

- 目标是本机共享 RuoYi 使用的 MySQL `ry-vue`，不是生产候选环境。迁移前只读查询确认 `fq_*` 业务表 0 张、`fashion_flyway_schema_history` 不存在，`sys_menu` 存在；Fashion 保留段菜单 ID 无冲突。
- 首阶段配置 Java↔Python 本机 HMAC 密钥与 Runtime 地址，并运行已批准的 Fashion V1 建表迁移。后续根据用户回复安装项目目录菜单。Provider、AI Worker 和外部调用保持关闭；未给角色授权、未写入业务样本或真实报价。
- 执行前使用 `mysqldump --single-transaction` 备份当前 `ry-vue` 至 `.runtime/backup/ry-vue-before-fashion-20260926.sql`（62,190 字节，SHA-256 `35743E2A48BB36B0E95E0B47EB9E3294E3C8AD5886FFBC6B35AED29BE0778514`）。备份包含本机账号等现有数据，位于 Git 忽略的 `.runtime/`，不得作为公开附件。

## 实际动作与结果

1. 使用系统安全随机数生成 32 字节密钥，将同一 key ID `fashion-local-20260926` 与 Base64 密钥写入 Git 忽略的根 `.env`，分别供 Java 的 `FASHION_SERVICE_ACTIVE_KEY_*` 和 Python 的 `FASHION_AI_AUTH_ACTIVE_KEY_*` 使用；另设置本机 Runtime URL `http://127.0.0.1:8100`，AI Worker 保持 `false`。配置回读确认两端 key ID 和密钥一致、解码后长度 32 字节；没有输出密钥正文。
2. 在独立 Java 进程上使用端口 `18081`、目标库校验 `ry-vue`、首次 baseline 明确开关和 Fashion 迁移开关，运行仓库现有的 Flyway V1。该进程关闭 APS、Aden、Fashion Workers 与外部 Provider，避免与共享服务的后台任务重叠。日志记录 baseline 0 成功、V1 成功；临时进程随后停止。
3. 建表后 MySQL 只读回查：精确 `fq_*` 表数为 **16**；Fashion Flyway 历史为 2 行，其中 V1 `success=1`；当时菜单记录为 **0**。
4. 重新启动 Python Runtime，使其读取新密钥。进程配置检查为 `configured=True`、32 字节、Provider `disabled`；`GET /health` 返回 200。再以本机 `ruoyi-fashion` 服务身份，对运行中 Python 的 `/internal/v1/capabilities` 发送一次按 HMAC v1 签名的只读请求，返回 200（523 字节），证明入站密钥实际生效。
5. 共享 RuoYi 的 `8081` 端口当时已被另一项本地操作释放；使用仓库 `ruoyi-backend/bin/run-local.ps1` 恢复服务，让它读取 `.env`。本次进程关闭 APS、Aden、AI Worker、图片 Worker 和外部 Provider；`GET /captchaImage` 返回 200。前端 `5173` 返回 200。

主要执行命令为 `mysqldump --single-transaction --routines --triggers --events --set-gtid-purged=OFF --result-file=.runtime/backup/ry-vue-before-fashion-20260926.sql ry-vue`（口令仅经进程环境传入）、`java -jar ruoyi-admin.jar --spring.profiles.active=druid,local --server.port=18081 --spring.quartz.auto-startup=false`（迁移开关与目标库经进程环境传入）、`pwsh -NoProfile -File ruoyi-backend/bin/run-local.ps1`，以及对 `ry-vue` 的只读 `information_schema` / Flyway 历史查询。备份、迁移和查询退出码均为 0。

## 限制与恢复

- 这次验证证明本机进程、密钥配置、迁移、Python 入站签名和选品页面能力查询可用；Java↔Python 已签名业务 Run、Provider 质量和业务验收尚未执行。AI Worker 仍关闭，因此不产生 Run 处理或费用。
- Python Runtime 当前 `ProviderMode` 只允许 `disabled`；本次配置的是 Java↔Python 服务认证密钥，不是模型平台 API Key。要产生真实分析结果，还需实现并验收 Provider 接入、发布 Agent 版本，再单独启用相应 Worker。
- 菜单脚本 `ruoyi-backend/sql/ruoyi-fashion-permissions.sql` 不自动授权角色。当前没有给任何角色新增 Fashion 授权；普通角色是否能看到菜单取决于后续明确授权。
- 停止条件是目标库不符、现存未知 `fq_*` 表、迁移失败或健康检查失败。当前未触发。若需恢复，先停止相关服务并核对迁移后有无新增业务数据；上述备份提供迁移前快照。不要在共享库上直接覆盖恢复或删除 16 表，须先确认实际影响与回滚授权。密钥需要轮换时，替换 `.env` 中两端相同的 key ID/密钥并重启对应进程。
- 本记录不表示上线就绪、真实 Provider 已启用或用户验收完成。

## 续办：安装项目目录菜单与页面联通

用户随后明确要求“安装菜单呢，新建一个目录，以项目作为一个目录就可以”。执行前只读确认菜单保留 ID、顶层 `fashion` 路径、组件与权限标识均无冲突。再次完整备份 `ry-vue` 至 `.runtime/backup/ry-vue-before-fashion-menu-20260926.sql`（118,650 字节，SHA-256 `51D2A18732D7A4F5EE2B39F1204FF8DAD9AE3B880F507CC06431F5103A7103D0`），然后通过 MySQL 客户端 `source ruoyi-backend/sql/ruoyi-fashion-permissions.sql` 安装现有脚本，退出码为 0。

回查 `sys_menu` 的 920000～920035 段共 **36** 条，其中顶层目录 `智能选品`（`menu_id=920000`、`path=fashion`）1 条、直属页面菜单 **13** 条；`sys_role_menu` 新增授权 **0** 条。`fq_*` 表仍为 **16** 张。

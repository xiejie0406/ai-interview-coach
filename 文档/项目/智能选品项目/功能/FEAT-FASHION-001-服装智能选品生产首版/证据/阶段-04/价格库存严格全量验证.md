## 1. 实现范围

- Java 实现价格与库存两套独立的固定 CSV/XLSX 模板、范围选择、严格全量预览、批次详情、原子发布和恢复预览；不增加价格版本、库存版本或核实表。
- 价格只更新 `fq_product.sale_price/currency/tax_mode/price_as_of/last_price_import_batch_id`；库存只更新 `fq_stock`；每行前值、目标值、应用结果和错误继续由 `fq_import_batch` 与 `fq_import_detail` 留痕。
- 预览冻结 `scope_hash`、`base_data_hash`、行版本和业务时间；发布时在公共 `FashionCatalogWriteLock` 内重读范围与版本，冲突不静默覆盖。
- 严格全量要求范围内所有有效 SKU 恰好出现一次；缺行、多行、重复键、未知 SKU、范围不符、过旧/过未来业务时间、非 CNY、税口径或数值错误均阻断整批。
- 价格和库存都明确接受数值 `0`；价格 `0` 表示当前价格数据存在但不可用于正式报价，正式报价仍必须大于 `0`。
- 恢复操作创建新 `restore` 批次，重新读取当前值并校验，再在新事务中写回历史前值；不移动所谓“当前版本指针”。
- Admin 新增价格全量更新、库存全量更新页面，共用严格预览组件，显示应覆盖/实际/错误行数、前值/目标值、缺失行、冲突重新校验和二次确认恢复。
- RuoYi 菜单和权限脚本区分 `fashion:price:import`、`fashion:stock:import`、`fashion:import:restore`，不自动为任何角色授权。

## 3. 隔离 MySQL 结果

最终场景在全新的临时 MySQL 8.0.46 上执行 RuoYi 基线、Fashion migration 和业务测试，得到：

- `imp04_products=2`、`imp04_stock_rows=2`；两个测试 SKU 均在隔离范围内；
- 价格 `0.00` 发布成功 `price_zero=1`，库存 `0` 发布成功；
- 价格和库存各完成一次新值发布后恢复至零值，`restore_success=2`；
- 缺少范围行与过旧业务时间各生成无效批次，`invalid_batches=2`，没有覆盖当前值；
- 发布前篡改商品 `row_version` 产生 `conflict_batches=1`，批次留存冲突状态；
- 在第二行人为注入数据库溢出时，第一行价格更新一同回滚，批次仍为待发布，`rollback_batch_validated=1`；
- 重复提交相同 request key 和摘要返回原结果，不重复发布；RuoYi `sys_role_menu` 自动授权为 `role_grants=0`。

临时实例在测试完成后正常停止，精确的 `.codex-tmp/fashion-mysql-imp04-*` 目录已移入 Windows 回收站；工作区既有 MySQL 服务未被修改或停止。

## 4. 发现与修正

| 发现 | 修正 |
| --- | --- |
| 原 DDL 的价格检查仅允许大于 `0`，与“显式零可生效、正式报价另行阻断”需求冲突 | 将 `fq_product.sale_price` 约束更正为可空或 `>= 0`，并同步数据库设计；后续报价仍校验 `> 0` |
| 重新预览若复用旧 `base_data_hash`，冲突后无法生成新批次 | 幂等摘要加入当前 `base_data_hash`，数据变更后的重新预览可建立新批次 |
| 现有 MySQL 测试断言全局库存行数为零，受新场景和 JUnit 方法顺序影响 | 改为只断言原 IMP-03 商品范围未写入库存，保持业务不污染语义 |
| Playwright 首次全套与生产构建并行时遇到环境资源超时 | 浏览器配置收敛为单 worker、120 s 场景上限，在构建完成后独立重跑，最终 3/3 通过 |
| 同一页面立即连续发起两次预览，测试可在首次 `finally` 解除加载前触发时序抖动 | 用例明确模拟运营人员修正文件后重新进入导入页，再执行第二次严格预览 |
| 权限 SQL 同一库存菜单更新重复两次 | 保留插入后的单次幂等更新，删除前置重复语句 |

执行中误用 `pnpm exec` 触发了本地依赖链接重建，且因 pnpm 构建脚本批准策略退出为 1；随后删除该次误生成的 `pnpm-lock.yaml` 与 `pnpm-workspace.yaml`，回到项目锁定的 `npm` 脚本入口。之后 Admin 类型、28 个单测和 Chrome 3/3 均重跑成功；该 pnpm 失败未计入 Pass。

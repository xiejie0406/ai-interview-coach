## 2. 执行摘要

### 2.1 结论先行

1. **生产排程市场不是一种产品。** 它至少分为 ERP/SCM/MOM 套件内置 APS、可与 ERP/MES 并存的专业 APS、面向中小制造的云制造一体化产品，以及 AI 驱动的相邻型生产协同平台。四类产品解决的核心问题、数据前提、交付周期和价格结构明显不同。`FIND-PS-001`
2. **成熟产品的共同流程不是“一键排程”，而是“取数/校验 -> 求解 -> 人工审查与修复 -> 发布 -> 执行反馈 -> 再求解”。** Oracle 将其明确写成创建、刷新、Solve、审查、调整、Release；PlanetTogether 也明确写出导入、定义目标、优化、人工调整和发布五步。`FIND-PS-002`
3. **有限产能只是入场券，真正差异在约束语义和治理。** 设备能力、工序关系、物料、人员/工具、班次、换型、固定期、替代资源、批量与目标权重如何建模，决定计划是否可执行；“支持有限产能”本身不足以证明适配目标工厂。`FIND-PS-003`
4. **实施工作量主要落在数据和集成，不只在算法。** 产品/BOM/Routing、工作中心、日历、库存、在途、工单状态、标准工时和实际反馈必须有明确事实源、刷新频率和回写规则。多家官方文档都把这些数据作为求解前提。`FIND-PS-004`
5. **防止计划频繁抖动是核心产品能力。** 成熟路线普遍提供 fixed time fence、firm/frozen、resource lock、局部修复、What-if 副本或发布边界，而不是每次异常都全局重排并覆盖正式计划。`FIND-PS-005`
6. **PRD 的设备有限产能主线与行业一致，但一期同时纳入人员技能、工装、物料齐套、插单模拟、现场闭环，已接近中高阶 APS/MOM 范围。** 若目标是先验证可用性，应把约束按业务价值和数据成熟度分级启用，而不是一次启用全部。`FIND-PS-006`
7. **人工计划不是算法失败后的补丁，而是产品正常流程。** 各代表产品均保留甘特图、优先级、锁定、替代资源、Repair 或规则切换等人工入口；关键是人工动作后仍进行约束校验并留下发布边界。`FIND-PS-007`
8. **“为什么排不上、为什么延期、改动会影响谁”是明显机会。** SAP 的 Alert Monitor、Oracle 的指标/pegging/Repair、Asprova 的关系图和 PlanetTogether 的约束可视化均在回答局部问题，但公开资料对统一的因果解释、版本差异和恢复建议披露有限。`FIND-PS-008`
9. **AI 更适合先做数据映射、规则配置、异常归因和方案解释，不应替代硬约束求解与发布校验。** 黑湖展示了读图、拆单、排程线索和 Agent 协作路线，但公开资料未说明其严格有限产能可行性、冲突证明和求解边界。`FIND-PS-009`
10. **本项目更可行的差异化不是复制 SAP/Siemens 的全套深度，而是面向中型离散制造提供“更快接入、更透明的数据质量、更可解释的局部重排、更清楚的计划版本与发布审计”。** `FIND-PS-010`

### 2.2 对 PRD 的阶段性判断

**分析推断：** PRD 的 `Operation Task` 最小排程对象、硬约束与软目标分离、计划版本化、算法服务化、甘特图人工计划和现场反馈闭环，方向总体正确，并与多个成熟产品的公开逻辑一致。

**分析推断：** 当前最大风险不是页面数量或算法选型，而是尚未明确首个目标行业、计划粒度、系统边界和数据事实源。注塑、机加工、装配、食品/化工的资源模型和换型规则差异很大；在未选定首个可重复行业模板前，“通用 APS”很容易变成长期定制项目。

**建议讨论的分期，不是已批准范围：**

| 建议验证层 | 先证明什么 | 典型能力 |
| --- | --- | --- |
| M0 数据可排 | 输入是否完整、一致、可追溯 | 产品/BOM/Routing、设备能力、日历、订单、缺失/冲突检查、数据来源与刷新时间 |
| M1 机器可行计划 | 关键设备上能否生成并人工维护可执行计划 | 工序依赖、设备有限产能、正/逆向、锁定、甘特图、冲突校验、场景副本、审核发布 |
| M2 多约束可行计划 | 关键业务约束能否稳定进入求解 | 物料齐套、人员技能/班次、工装、换型矩阵、批量/重叠、替代资源、局部重排 |
| M3 计划执行闭环 | 现场变化能否受控回流并校准模型 | 开停完工、异常、计划/实际偏差、滚动刷新、原因解释、参数校准 |

## 3. PRD 目标与本次调研决策问题

### 3.1 PRD 明确表达的目标

**官方事实（本地原始 PRD）：**

- 面向多产品、多零件、多工序、多车间、多设备、多人员的有限产能生产排程。
- 从生产订单展开 BOM 和工艺路线，以工序任务作为最小排程对象。
- 对工序任务分配开始/结束时间、车间/工作中心、设备、人员/班组、工装及前后置关系。
- 在工序依赖、设备能力、资源冲突、人员技能、日历、物料和批量等硬约束下，优化交期、利用率、换型、在制品、人员负载和订单优先级。
- 支持资源甘特图、人工拖拽、换设备、换人员、锁定、插单模拟、影响分析和局部/整体重排。
- 发布至车间后记录开工、暂停、完工、报工和异常，保留计划值与实际值。
- 一期建议先建立“数据正确、有限产能可排、人工可调、现场可反馈”的闭环。

## 6. 代表竞品逐一研究

### 6.1 SAP S/4HANA Production Planning and Detailed Scheduling

**定位与客户**

- **官方事实：** SAP 将 PP/DS 用于关键产品、长补货周期产品和瓶颈资源，目标是详细计划资源负荷与订单日期，并同时考虑资源和组件可用性。[PP/DS 2025 FPS01 帮助](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/f899ce30af9044299d573ea30b533f1c/0e1c0651de86d406e10000000a44176d-1594.html)
- **分析推断：** 最适合已经以 SAP 为订单、库存、采购和生产订单事实源，且愿意承担较强主数据与配置治理的企业。

**核心流程与排程逻辑**

- **官方事实：** 主数据和销售订单、库存等交易数据从 S/4HANA 进入 PP/DS；PP/DS 使用 production planning run、heuristics、detailed scheduling 和 optimizer，结果再回到 S/4HANA 执行。
- **官方事实：** 交互计划板可按策略执行有限产能排程、拖拽改时间或改替代资源；Alert Monitor 用于异常管理；pegging 连接库存、收货与需求，传播多层 BOM 的日期问题。
- **官方事实：** optimizer 用成本表达软约束；交期或安全库存可作为带违约成本的软约束。换型矩阵根据前后工序的 setup group/key 计算顺序相关换型时间和成本。[优化说明](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/f899ce30af9044299d573ea30b533f1c/75ad7241a22047ba8758b19c42ac193c.html) [换型矩阵](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/f899ce30af9044299d573ea30b533f1c/8e4ec95360267614e10000000a174cb4.html)

**集成、落地与商业模式**

- **官方事实：** SAP 公开了 embedded/side-by-side 相关实施资料；side-by-side 可连接一个或多个 ERP，但需要专门配置与客户化实施。[2023.5 实施指南](https://help.sap.com/doc/dd8e043bcf4f4cde82906956b8bdce96/2023/en-US/SAP_S4HANA_DSCEdition_PPDS_Implementation_Guide.pdf)
- **官方事实：** SAP 文档对 setup matrix、fixing interval、订单重新展开和 technically closed order 有明确限制，说明主数据及生命周期动作会改变既有排程结果。
- **商业信息：** 本次所查官方产品/帮助页未找到 PP/DS 的独立公开金额，需按 SAP 产品组合、部署和合同询价。

**对本项目的启示**

- 把“策略配置、启发式、优化器、人工计划”视为不同执行模式，不应只提供一个黑盒“智能排程”按钮。
- 软目标必须有可解释的成本/权重模型；换型矩阵需要版本、适用资源和变更影响控制。
- SAP 的复杂度也说明，一期不应复制全部 PP/DS 对象和配置面板。

### 6.2 Siemens Opcenter Advanced Planning and Scheduling

**定位与客户**

- **官方事实：** Opcenter APS 分为长期/中期的 Opcenter Planning 和详细排序的 Opcenter Scheduling，覆盖资源、约束、物料和订单优先级。[产品家族页](https://www.siemens.com/en-us/products/opcenter/advanced-planning-scheduling-aps/)
- **分析推断：** 适合有复杂生产约束、需要独立 APS，也可能逐步与 Opcenter MOM/MES 组合的中大型制造企业。

**核心流程与排程逻辑**

- **官方事实：** Scheduling 支持按订单排名或加权、多约束排程、不同设备速度、顺序相关换型、工序重叠/间隔、并发资源和跨工序约束；物料可按质量或客户规则过滤和排序。[Advanced Scheduling](https://www.siemens.com/en-us/products/opcenter/advanced-planning-scheduling-aps/advanced-scheduling-software/)
- **官方事实：** primary resources 常用于机器，secondary resources 可用于工具或劳动力；班次外时段可作为 secondary constraint 日历。系统提供物料依赖图、库存曲线、只读发布计划查看和现场待办。
- **官方事实：** 可独立运行，也可与 ERP、MES、数据采集、预测、需求计划和 OEE 应用集成；可配置数据库结构和约束模型而不改核心代码。

**实施与商业模式**

- **官方案例：** Natural One 在实施前通过跨部门访谈厘清限制，使用 Planning 形成周 MPS，再把选定产量传给 Scheduling 做批量与换型排序。厂商案例称计划时间和缺货率改善，但仅适用于该饮料工厂。[Natural One 案例](https://resources.sw.siemens.com/en-GB/case-study-natural-one-opcenter/)
- **官方事实：** 官网提供试用入口和 Contact Sales，但本次未找到公开正式许可金额。

**对本项目的启示**

- “计划量/主计划”与“工序级排序”是两个层次，PRD 需确认一期是否两者都做。
- 约束模型可扩展比固定列更重要，但扩展必须受版本与测试保护，不能演变成每客户一套不可维护代码。

### 6.3 Oracle Fusion Cloud Supply Planning Production Scheduling

**定位与客户**

- **官方事实：** Production Scheduling 属于 Oracle Fusion Cloud Supply Planning/SCM 体系，面向已有 Oracle Supply Planning、Manufacturing 和 Work Execution 数据的工厂。[产品页](https://www.oracle.com/scm/supply-chain-planning/supply-planning/)
- **分析推断：** 对 Oracle Cloud SCM 用户的价值主要来自计划与执行数据内置集成，而不是作为轻量独立排程器。

**核心流程与排程逻辑**

- **官方事实：** 官方工作流是设置 scheduling organization，创建 schedule，refresh、solve、review、adjust，最后 release。[26B 工作流](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/fapsu/production-scheduling-tasks-and-business-flows.html)
- **官方事实：** schedule 参数包含 fixed time fence、resource constraint horizon、release horizon 和 lateness tolerance；resource 可设 Constrained、Relaxed 或只放松产能，未配置时默认是 Relaxed。[Schedule Parameters](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/fapsu/schedule-parameters.html) [Resource Parameters](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/fapsu/resource-parameters.html)
- **官方事实：** 甘特图拖拽、dispatch list 重排或替代资源调整后，需要 Repair 才完成正确生产率和换型插入；可 firm 操作，随后 Solve 对齐上下游。[Solve and Repair](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/fapsu/solve-and-repair-behavior.html)
- **官方事实：** 支持按属性定义 cleanup/setup 换型规则、并行或顺序换型、用户指定属性序列、物料入库情景和 minimum transfer quantity 造成的工序重叠。

**集成、落地与商业模式**

- **官方事实：** Release 会回写工单及工序开始/结束、资源分配、可选状态和 firm 标记；计划单与工单的可发布边界不同。[Release](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26b/fapsu/release-analysis-and-actions.html)
- **商业信息：** 本次在官方产品和 26B 文档中未找到 Production Scheduling 独立公开价，需按 Oracle Cloud SCM 订阅组合询价。

**对本项目的启示**

- “拖完即保存”不足以保证可行，应明确 `人工改动 -> 约束修复/校验 -> 审核 -> 发布`。

### 7.2 排程对象和数据模型

| 观察 | 行业做法 | 对本项目的含义 |
| --- | --- | --- |
| 最小对象 | 主流详细排程都落到 order operation/operation task，而非只给订单起止日 | PRD 的 `Operation Task` 正确；还需定义 lot split、overlap、返工和外协的对象语义 |
| 资源 | 机器/工作中心通常是 primary resource，人员、工具、模具常作为 secondary resource 或容量池 | 不要强迫所有资源共用完全相同表结构和冲突算法；先定义统一能力，再允许类型特有规则 |
| 工艺 | Routing/PDS/work definition 不只是顺序，还包含替代资源、速度、批量、重叠、最小转移量和等待 | DAG 是合理底座，但需限制一期可编辑的关系类型 |
| 物料 | 成熟产品使用库存、在途、采购/计划供给与 pegging 判断最早可开工 | “齐套”需定义是全部齐套、关键料齐套、软约束还是可人工豁免 |
| 日历 | 资源日历、班次、维修、固定期和例外共同决定可用时间 | 日历合并优先级与时区必须形成确定规则，并能解释某时间窗为何不可用 |

### 7.3 求解与目标逻辑

**官方事实汇总：** 代表产品并非只有一种算法。SAP 区分 heuristic、detailed scheduling function 与 optimizer；Asprova 使用可组合 command、dispatching rule 和 resource evaluation；Siemens 采用排序/权重与可配置优化规则；Oracle 使用 Solve/Repair、属性序列和资源 constraint mode；PlanetTogether 用 optimization factors 给规则引擎配置业务权重。

**分析推断：** 本项目一期更适合“确定性可行排程 + 可解释派工规则 + 局部搜索/优化”，而不是先承诺全局最优。建议结果至少携带：

- 使用的排程版本、输入快照和规则版本；
- 启用/放松的约束清单；
- 每个任务的候选资源、最终选择与原因码；
- 未排任务和延期任务的首要阻塞原因；
- 目标指标及相对基线变化，不把单一总分当作解释；
- 求解耗时、是否中止、是否找到可行解及 gap/近似边界（若算法能提供）。

### 7.4 人工调整、模拟和正式发布

成熟交互通常分为四层：

1. **查看：** 资源甘特图、订单甘特图、负荷、缺料、延期和瓶颈。
2. **尝试：** 在 Scenario 中拖拽、换资源、改优先级、加班或模拟停机，Live 不变。
3. **修复与校验：** 对人工计划重新插入换型、检查依赖/资源/物料，必要时修复上下游。
4. **发布：** 只把选定 horizon 和对象写回执行系统，记录批准人、版本、时间及差异。

**分析推断：** PRD 已有模拟、锁定和发布概念，但还缺 `Draft -> Solving -> Solved/Partial/Failed -> Reviewed -> Published -> Superseded/Cancelled` 的明确状态，以及发布失败、部分回写和撤回后的恢复规则。

### 7.5 动态重排与计划稳定性

- **官方事实：** SAP 使用 fixing interval、固定日期和可选择反应的 planning procedure；Oracle 使用 fixed time fence、firm status、Repair 和 release horizon；DELMIA 可按机器设置 fixed period；Asprova 有 released/frozen 与 resource lock；PlanetTogether 把 What-if 与 Live 分开。
- **分析推断：** 计划稳定性应成为一个显式目标：最小化已发布任务的时间/资源变化、避免频繁改派、保护已备料和已通知班组的任务。
- **不建议：** 任何现场事件都自动全局重排并立即覆盖正式计划。默认应做影响分析和局部候选方案，超过阈值再升级人工决策。

### 7.6 集成和事实源

典型数据方向如下：

| 数据 | 常见事实源 | APS 主要用途 | 回写/消费方 |
| --- | --- | --- | --- |
| 产品、BOM、Routing、版本 | ERP/PLM | 任务展开、依赖、时间和候选资源 | APS 缓存与版本引用 |
| 订单、交期、优先级 | ERP/OMS | 排程需求 | ERP 获取承诺/计划日期 |
| 库存、采购、在途 | ERP/WMS/SRM | 物料最早可用、pegging | 采购催办、缺料预警 |
| 设备、能力、维修 | MES/EAM/APS 主数据 | 有限产能与替代资源 | MES/派工看板 |
| 人员、技能、班次 | HR/MES/APS 主数据 | 劳动力约束 | 班组/个人任务 |
| 工单执行、报工、异常 | MES/工位终端 | 刷新剩余工时和局部重排 | APS 计划实际对比 |
| 排程结果、版本、发布状态 | APS | 正式计划与可承诺日期 | ERP/MES/WMS/通知系统 |

**待验证假设：** 本项目可能需要同时支持 CSV 首次导入和 API 增量同步。两者可以共用同一 canonical schema，但必须定义幂等键、删除/撤销语义、源版本、迟到事件、冲突处理和回写确认。

## 8. 行业共性做法

### 8.1 可执行计划闭环

1. 明确计划组织、horizon、时间粒度和输入快照。
2. 先做数据就绪检查，缺基础数据的订单进入问题队列，不直接静默猜值。
3. 展开 BOM/Routing，形成工序网络和候选资源集合。
4. 先满足硬约束，再依据业务目标、派工规则或优化器选择顺序与资源。
5. 输出未排、延期、缺料、超负荷和换型等例外，而不只输出甘特图。
6. 计划员在独立场景中调整，系统重新 Repair/Validate。
7. 审核并发布冻结范围，按对象和 horizon 回写执行系统。
8. 现场反馈实际开始/结束、产量、停机和异常，刷新未来未执行部分。
9. 用计划/实际偏差校准标准工时、良率、停机和换型参数，但变更需审核与版本化。

### 8.2 产品与实施共性

- 先找瓶颈资源和高价值订单，不要求第一天覆盖所有工厂和所有约束。
- 把计划员经验转为规则、参数和回归样例，保留人工最终控制。
- 使用场景副本评估急单、停机、加班、外协和交期变化，正式计划单独发布。
- 短期冻结、中期滚动、长期粗计划采用不同粒度和约束强度。
- 先统一编码、日历、BOM/Routing 和标准工时，再讨论高级优化收益。
- 上线不是一次结束；需要持续治理数据质量、规则、目标权重和计划遵从率。

## 9. 常见失败点与实施难点

| FIND | 失败点 | 典型表现 | 建议验证或缓解 |
| --- | --- | --- | --- |
| FIND-PS-011 | 主数据不可信 | 求解成功但现场无法执行；大量人工改表 | 上线前做数据就绪评分、缺失原因和责任人队列 |
| FIND-PS-012 | 计划与执行事实源冲突 | ERP、MES、Excel 对同一工单状态不同 | 建立字段级 owner、刷新频率、冲突优先级和审计日志 |
| FIND-PS-013 | 约束建模过度 | 参数很多、求解慢、无人敢改 | 按业务价值分级启用；每项约束配样例和回归测试 |
| FIND-PS-014 | 目标权重没有业务共识 | 设备利用率提高却造成更多延期或库存 | 用多 KPI 展示权衡，保存权重版本并做基线对比 |
| FIND-PS-015 | 计划频繁抖动 | 班组反复换任务、备料失效、系统失去信任 | fixed horizon、锁定、变更惩罚、局部重排和发布审批 |
| FIND-PS-016 | 人员约束数据过细或过旧 | 排到个人后因请假/换班立即失效 | 一期先班组/技能池，确有刚性需求再排到个人 |
| FIND-PS-017 | 物料可用时间过于乐观 | 有库存但未质检/未配送，仍停工待料 | 区分现货、已分配、在途、质检、线边和替代料状态 |
| FIND-PS-018 | 人工拖拽绕过校验 | 甘特图看起来合理但存在资源或依赖冲突 | 人工改动进入草稿，必须 Repair/Validate 才可发布 |
| FIND-PS-019 | 一开始覆盖太多行业 | 核心模型被大量客户特例污染 | 先选一个行业模板和 3 至 5 个代表性排程场景 |
| FIND-PS-020 | 自动重排直接覆盖正式计划 | 现场收到互相矛盾的任务 | 模拟与正式隔离，发布具备幂等、部分失败和回滚处理 |
| FIND-PS-021 | 只看厂商收益数字 | PoC 目标不清，无法判断真实价值 | 用客户自己的历史订单做 baseline 与盲测，预注册指标 |

## 10. 对本项目可借鉴与不建议照搬

### 10.1 建议借鉴

1. **Oracle 的显式工作流：** Refresh、Solve、Review、Adjust/Repair、Release 分开，状态和失败容易解释。
2. **PlanetTogether 的 Live/Scenario 隔离：** 模拟不污染正式计划，发布才产生执行影响。
3. **SAP 的约束与目标分离：** 硬约束决定可行性，软目标用权重/成本权衡，Alert 管理例外。
4. **Siemens/Asprova 的约束模板：** 派工规则和行业约束可配置、可组合，但需版本和回归样例。
5. **DELMIA 的 core model 滚动复制：** 先验证一套核心工厂模型，再扩展多工厂和局部差异。
6. **MRPeasy 的低门槛闭环：** BOM、订单、排程、工位/个人任务和现场报告连起来，避免只有算法演示。
7. **国内厂商的行业模板表达：** 直接说清机加工、注塑、电子装配的特有约束，比泛化功能清单更容易销售和验收。
8. **AI 的辅助位置：** 读取文档、建议工艺、解释异常、辅助规则配置；硬约束和发布仍由确定性系统把关。

### 10.2 不建议照搬

- 不在一期复制大型 ERP、MES、WMS、EAM、HR 和 SCM 全套功能。
- 不先做“覆盖所有行业”的通用约束编辑器；先以一个行业模板验证对象模型。
- 不把“全局最优”作为销售承诺；先证明可行、稳定、可解释和比人工计划基线更好。
- 不默认把每名员工作为有限资源；个人排程需要可靠技能、班次、请假和现场替换数据。
- 不允许计划员直接修改已发布版本；修改应产生新草稿/场景和差异记录。
- 不让 AI 直接绕过求解器写正式任务，也不让自然语言输出成为唯一审计依据。
- 不只做漂亮甘特图；未排原因、缺料、瓶颈、版本差异和发布结果更接近实际工作价值。
- 不以厂商案例的百分比作为本项目 KPI；必须用目标客户自己的基线设定成功标准。

## 11. 差异化机会

| 机会 | 用户价值 | 可验证的首版形式 |
| --- | --- | --- |
| 数据就绪中心 | 在求解前知道“为什么不能排” | 按订单列缺 BOM/Routing/工时/日历/候选资源及责任人 |
| 可解释排程 | 计划员能判断并信任结果 | 任务原因码、候选资源淘汰原因、延期因果链、约束开关快照 |
| 稳定性优先的局部重排 | 现场少受扰动 | 显示受影响任务数、时间/资源变更量、冻结冲突和推荐方案 |
| 场景对比而非单一答案 | 支持真实业务权衡 | 急单/加班/外协三方案并列比较交期、换型、WIP 和改动量 |
| 开放且可渐进的接入 | 降低中型企业首期成本 | 同一 canonical schema 支持 Excel/CSV 和 API，提供同步状态页 |
| 行业约束包 | 缩短从演示到可用的距离 | 先做机加工或注塑包，内含字段、规则、样例订单和验收集 |
| 人机协同 AI | 减少配置和解释成本 | AI 提取订单/图纸形成草稿、解释异常、生成规则建议，人工确认 |
| 计划版本与发布审计 | 出错可定位、可恢复 | Draft/Scenario/Published/Superseded 状态、差异、回写回执和撤回策略 |

**分析推断：** 最值得聚焦的产品句子不是“AI 自动排程”，而是“把工厂现有订单和工艺快速变成一份可解释、可人工控制、可受控发布的有限产能计划”。这仍需用户确认目标客户后才能成为正式定位。

## 12. 建议与用户讨论的问题

1. 首个客户更像机加工、注塑、电子装配、食品/化工，还是其他行业？
2. 首版服务单工厂单车间，还是从一开始就必须多工厂协同？
3. 客户当前主要使用 Excel，还是已经有 ERP/MES/WMS？具体品牌和可用接口是什么？
4. 首版必须做到工作中心、单台设备、班组还是个人级排程？
5. 人员技能是严格约束，还是只需给班组能力预警？
6. 物料齐套是 P0 硬约束吗？“可用”具体包括库存、在途、质检、线边和替代料中的哪些状态？
7. 首版最重要的优化目标是准时交付、瓶颈利用率、减少换型、降低 WIP，还是计划稳定性？请排序。
8. 急单进入后，系统只给影响方案，还是允许用户确认后自动形成新计划？谁有发布权限？
9. 已开工、已备料、已通知班组和近 24/48/72 小时任务分别允许改到什么程度？
10. 是否需要倒排后给销售做 ATP/CTP？承诺日期是否必须带有效期和假设条件？
11. 现场执行是本系统自己做开工/暂停/完工，还是只与现有 MES 交换状态？
12. 首版是否接受 CSV/Excel 定时交换，还是必须实时 API/消息同步？
13. 部署必须私有化、本地离线可运行，还是可接受公有云 SaaS？
14. 目标商业模式偏按用户订阅、按工厂/资源订阅，还是软件许可加实施服务？
15. 选择 3 至 5 个真实历史订单做 PoC 时，什么结果能证明值得继续：可行率、人工计划节省时间、延期下降、换型下降还是改动稳定性？

## 15. 证据缺口与下一步调研建议

### 15.1 当前证据缺口

- 没有使用统一历史订单数据运行 11 个产品，无法比较求解速度、可行率、计划质量和人工计划成本。
- 缺少 SAP、Siemens、Oracle、DELMIA、Asprova、鼎捷、金蝶、黑湖和安达发的可比报价，暂不能估算总拥有成本。
- 多数厂商未公开完整算法、并发规模、最优性 gap、失败码、版本回滚和 API SLA。
- 国内厂商公开页面多为品牌级产品说明，具体 SKU、版本、部署方式和“内置 APS/第三方 APS/辅助派工”的边界需演示确认。
- 尚无本项目目标客户的真实数据质量、人工计划流程、插单频率和收益基线。

### 15.2 用户选定目标行业后的最小补充验证

1. 准备 3 至 5 个脱敏历史订单，包含 BOM、Routing、设备日历、工时、物料和实际结果。
2. 设计固定演示脚本：普通排程、同机冲突、技能不足、维修、人工拖拽、锁定、急单和现场延误。
3. 要求候选厂商现场展示每个场景的输入、约束开关、原因、人工计划校验、发布和恢复，不接受只播放视频。
4. 用同一指标比较：数据准备工时、求解时间、可行率、延期、换型、WIP、已发布任务改动量和计划员操作数。
5. 单独询价许可/订阅、实施、接口、培训、升级、测试环境、灾备和退出数据导出，形成三年 TCO。

## 1. 决定

生产排程前端不要求一个组件同时承担任务网络、资源泳道、负荷计算和自动排程。采用两个免费且许可宽松的组件，并按各自原生数据模型分工：

| 组件 | 负责视图 | 不承担的责任 |
| --- | --- | --- |
| `DHTMLX Gantt Community v10+` | 订单、产品、工艺路线、工序任务树、里程碑及产品领域已经支持的依赖关系；组件本身可绘制 FS / SS / FF / SF | 人员 / 设备资源管理、资源日历、资源负荷、自动排程、关键路径及其他 PRO 能力；组件能画的依赖不自动成为产品能力 |
| `vis-timeline` | 车间、工作中心、人员、设备资源行；准备 / 运行 / 卸料时间段；同一资源行多任务；跨资源行调整 | 工序依赖引擎、任务树、资源容量计算、逐资源工作日历、自动排程和计划发布 |

两个依赖和隔离适配器已经作为 IMP-01 技术 PoC 接入，但还没有接入业务 API、路由、Store 或生产工作台。当前 V2 仍是原生 HTML / CSS / JavaScript 业务原型，只作为交互与规则对照。500 资源行 / 5,000 分段实测证明了真实组件能够渲染、销毁和重建，不等于交互性能、业务场景或生产方案已经验收。

## 2. 选择依据

两类核心页面的纵轴不同，强行使用同一种模型会产生大量组件内部改造：

- 订单 / 工艺视角的纵轴是任务，重点是任务树、进度、里程碑和依赖线，适合 DHTMLX Community。
- 人员 / 设备 / 车间视角的纵轴是资源，一条资源行会出现多个时间段任务，重点是占用和跨行调整，适合 `vis-timeline`。
- 自动排程、技能、班次、数量释放、合批和交期优化属于领域服务，不能交给前端图表决定。

DHTMLX 官方矩阵明确将 Resource management、资源 / 项目日历、自动排程、关键路径、基线和任务分组等列为 PRO 能力；Community v10+ 仍包含任务树、四类依赖、拖拽和 Smart Rendering。`vis-timeline` 官方数据模型提供 `groups`、`nestedGroups`、范围 `items`、时间拖动及 `updateGroup` 跨组拖动，但没有完整项目甘特或 APS 引擎。

## 3. 架构边界

```mermaid
flowchart LR
  API[排程查询 / 调整 API] --> VM[前端排程视图模型]
  VM --> GA[DHTMLX Gantt 适配器]
  VM --> TA[vis-timeline 适配器]
  GA --> ROUTE[订单 / 工艺路线甘特]
  TA --> RESOURCE[人员 / 设备 / 车间时间轴]
  ROUTE --> CMD[调整建议命令]
  RESOURCE --> CMD
  CMD --> VALIDATE[后端约束校验与影响计算]
  VALIDATE -->|通过| DRAFT[候选计划版本]
  VALIDATE -->|拒绝| ROLLBACK[恢复原显示并返回冲突]
```

必须遵守以下边界：

1. 业务实体、数据库和 API 不保存 DHTMLX 的 `task` 对象或 vis 的 `item` 对象；组件对象只在前端适配层生成。
2. 两个视图使用相同的 `taskId`、`segmentId`、`resourceId`、`planVersionId`，选择或刷新时可以互相定位，但不互相复制业务状态。
3. 前端拖动、拉伸或跨行移动只产生调整建议。后端复验依赖、数量、技能、日历、资源冲突、锁定和已执行事实后，才返回新的候选版本。
4. 组件自带的拖拽限制只用于即时提示，不能代替服务端校验；校验失败必须恢复到服务端确认的计划位置。
5. 正式计划发布、版本比较、撤销、报工和审计不由组件本地状态决定。

## 4. 统一数据映射

| 领域对象 | DHTMLX Community 映射 | `vis-timeline` 映射 |
| --- | --- | --- |
| 订单 / 产品实例 | 项目或父任务 | 筛选条件及任务标签，不作为资源行 |
| 工序任务 | 普通任务 / 里程碑 | 一个或多个可视时间段的业务来源 |
| 工序依赖 | 仅把领域已支持的 FINISH、数量门槛和转移关系适配为可视 dependency；不启用未建模的同步语义 | 不常驻绘制；选中任务时由详情或工艺视图展示 |
| 车间 / 工作中心 | 任务字段或过滤维度 | `group` / `nestedGroup` |
| 人员 / 设备 | 任务资源摘要；不使用 CE 冒充资源管理 | 具体 `group` |
| 准备 / 运行 / 卸料 | 可按需要显示拆分摘要 | 独立 range item，均引用同一 `taskId` |
| 人机协同任务 | 显示工序任务和资源摘要 | 人员与设备视角分别生成关联占用项，不重复业务任务 |
| 共享加工批次 | 批次摘要与成员关系 | 设备占用只显示一次，详情展开成员，避免重复机时 |
| 非工作 / 维修 / 请假 | 由服务端计划结果和提示表达 | 背景时间块；可行性仍由逐资源日历服务判定 |

## 5. 明确不使用的能力

- 不下载、复制或依赖未授权的 DHTMLX PRO 包、破解包、试用包生产运行文件或 PRO 示例源码。
- 不把 DHTMLX 官网的 PRO 资源视图、自动排程或负荷演示记录为 Community 已具备。
- 不把 `vis-timeline` 宣称为完整甘特图、APS 求解器或 Bryntum Scheduler Pro 的免费等价物。
- 不在两个组件内部各维护一套可发布计划，也不允许前端绕过后端直接写正式分配。

## 7. PoC 验收

两个组件使用同一份脱敏排程数据验证，不能分别使用只对自身有利的样例。至少覆盖：

1. DHTMLX 展示多产品订单、工艺任务树、当前领域已支持的完成 / 数量 / 转移关系、里程碑、拖动建议及后端拒绝回滚；另用隔离样例确认组件可绘制四类依赖，但不得据此开启未建模的产品语义。
2. vis 展示车间层级、人员和设备资源行、一行多个时间段、跨资源移动、准备 / 运行 / 卸料及非工作背景。
3. 同一工序同时占用人员和设备时，两个可视占用保持关联，调整不产生重复业务任务或重复工时。
4. 共享加工批次在设备视角只扣一次资源时间，成员数量和订单归属可追溯。
5. 先验证 500 条资源行、5,000 个可见分段的滚动、缩放、筛选和重绘，再按 PRD 的 20,000 道任务规模使用时间窗和服务端分页执行容量测试。
6. 页面切换、筛选、选择联动、键盘操作、窄屏降级以及销毁重建无内存持续增长。
7. 所有调整都能处理成功、业务拒绝、网络失败、超时和版本过期，不把显示成功当作计划已保存。

PoC 未通过时，先判断是适配实现、数据窗口还是组件模型问题；若必须大量修改组件内部布局或绕过许可证能力，退出该候选并重新评估，而不是把 PRO 功能名称写进自研承诺。

### 7.1 IMP-01 已执行的技术 PoC

2026-09-12 在 Windows x86_64、Node.js `24.15.0`、npm `11.12.1` 和系统 Chrome `152.0.7977.83` 上，以同一份合成领域模型执行真实组件测试：

- 500 个资源、5,000 个可见分段完成首次渲染、双组件销毁清空、重新创建、再次渲染和二次销毁；浏览器 `console` 与 `pageerror` 均为空。
- 三次收口复核的双帧首屏 ready 位于约 `4,906.3～11,575.0 ms`；当前 lockfile 重装后的最近一次 DHTMLX 约 `546.1 ms`、vis-timeline 约 `6,206.0 ms`、ready 约 `8,982.0 ms`。该次用例因首次依赖预构建约 `1.5 min`，整次命令约 `2.7 min`。明显的运行间波动和 vis 主耗时都已保留，这些数值只对应当前机器和合成夹具，不是生产 SLA。
- DHTMLX 拖动只产生七个领域意图字段，并立即重新解析当前服务端确认模型；vis 调整使用 `accept(null)`。两者都不在本地把拖动结果冒充已保存计划。
- 因首屏观测范围约 4.9～11.6 秒且 vis-timeline 占主要耗时，结论为**受限 Go**：保留选型与适配层，在 IMP-08 进入正式工作台前必须锁定目标硬件、交互性能预算，并验证时间窗口、服务端分页/筛选和增量重绘。

本次只关闭技术适配、许可证、基础映射、回滚和生命周期证据。第 7 节中的共享批、人机协同、跨资源调整、滚动/缩放/筛选、键盘、窄屏、网络失败、超时和版本过期仍属于 IMP-08 的业务组件与浏览器验收，不能因本次 PoC 通过而标记完成。命令、环境和限制见[IMP-01 验证记录](../功能/FEAT-APS-001-生产排程核心闭环/验证记录.md)。

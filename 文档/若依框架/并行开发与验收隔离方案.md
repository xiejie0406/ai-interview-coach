## 1. 目标与实际问题

隔离单位是开发任务。同一业务项目内的两个并行任务也需要不同工作树；每个工作树保留完整仓库结构，并只修改本任务范围。后端继续沿用一个 `ruoyi-admin` 装配业务 HTTP 模块的架构，开发环境可运行多份对应不同代码版本的实例。

2026-09-26 本任务只读核查结果：

| 对象 | 实际观察 | 影响 |
|---|---|---|
| Git 工作树 | `git worktree list --porcelain` 仅列出 `D:/2025Ai/26-05-23/java-workspace`，分支 `main` | 当前尚无 Git 工作树隔离 |
| 当前修改 | `git status --short` 返回 4013 条状态记录 | 不能将旧 HEAD 当作当前完整基线，也不能把全部差异直接归入某个任务；记录数不等同于文件数，且会随其他任务变化 |
| [后端启动脚本](../../ruoyi-backend/bin/run-local.ps1) | 使用根 `.env`、固定 `target/ruoyi-admin.jar`、固定日志名，只检查 8081 监听 | 不足以区分任务版本、进程所有者和运行环境 |
| [管理端代理](../../frontend/admin-web/vite.config.js) | 后端目标固定 `127.0.0.1:8081` | 即使前端另开端口，仍可能访问公共后端 |
| [门户代理](../../frontend/portal-web/vite.config.ts) | HTTP、WebSocket 目标均固定 8081 | HTTP 和 WebSocket 都需要按任务绑定 |

这些观察证明存在共享路径和固定路由，不能据此认定某个任务造成了某次具体故障。本次未检查数据库实际连接、内存容量或浏览器跨任务登录态隔离，未读取 `.env` 秘密正文。

## 2. 目标布局与资源用法

下表为待实施示例，目录、域名和端口均未创建或分配；实施时先检查占用，并记录最终值。

| 环境 | 代码 | 前端入口示例 | 后端示例 | 数据与运行目录 |
|---|---|---|---|---|
| 当前工作区 | 保留现有全部修改，先完成迁移准备 | 维持当前实际配置 | 维持当前实际服务 | 未完成归属核对前不复用为新任务环境 |
| 任务 A | 独立完整 worktree；独立 `codex/<任务标识>` 分支 | `task-a.localhost:15173` | `127.0.0.1:18091` | A 的测试库、Redis 实例、配置、日志、文件和产物 |
| 任务 B | 另一个完整 worktree；另一个任务分支 | `task-b.localhost:15174` | `127.0.0.1:18092` | B 的测试库、Redis 实例、配置、日志、文件和产物 |
| 集成环境 | 指定基线加已选定任务修改；单一写入负责人 | 独立集成入口 | 独立集成实例 | 集成测试数据，合并后进行关联回归 |

不同主机名隔离浏览器站点状态，不同监听端口避免服务争抢；两者都需要核对。

建议先支持两个同时运行的验收环境，再依据 Java 堆、数据库连接数、构建耗时和实际内存压力扩容。四个开发任务可以同时编辑各自目录，但不必一直运行四套后端。只改文档或尚不需要联调的任务不启动服务；需要同时验收的两个任务各运行自己的实例。任何受占用验收环境都不能被另一个任务替换版本。

当两个并行任务都修改后端并需要运行验收时，会有两个独立 JVM，以及各自版本的 JAR；如果从源码启动，则同样需要各自的进程和构建目录。APS Worker、Python Runtime、桌面 Runner 只在场景需要时按任务配置并启动。

## 3. 必须一并隔离的内容

| 层次 | 实施要求 | 完成证据 |
|---|---|---|
| 代码 | 每个任务绑定自己的绝对工作目录和基线；不访问另一任务目录修改代码 | 任务记录与 `git worktree list` 一致；双方修改互不可见 |
| 构建 | `target`、`dist`、可写 `node_modules` 各自独立；禁止将工作树可写目录链接到公共目录 | A 构建、清理不会改动 B 的输出 |
| 本地依赖 | 优先从各自 Maven reactor 构建所需模块及依赖；并行安装同坐标 SNAPSHOT 时使用任务专属 Maven 本地仓库 | 构建不会消费另一任务刚安装的未验证公共模块 |
| 后端进程 | 每个任务明确端口、PID、进程启动时间、工作目录、配置引用和产物哈希 | 停止/重启只能匹配本任务进程；端口被他人占用时报错 |
| 前端路由 | HTTP、WebSocket、下载地址和其他运行时 API 地址全部绑定本任务后端 | 浏览器网络请求与服务身份回读匹配 |
| 数据 | 每任务独立平台 MySQL 库；面试业务独立 PostgreSQL 库；其他业务按现有边界配置独立 MySQL 库 | 合成样本写入 A 后 B 不出现；数据库账号权限限制到本任务测试库 |
| Redis | 初期采用任务独立实例及端口；只在确认键、锁、缓存、订阅等均隔离后才考虑共享 | 键、分布式锁、Pub/Sub 不跨任务；仅换逻辑 DB 不能作为完整隔离证明 |
| 后台工作 | 定时器、消息消费、APS Worker、Python/Runner 明确任务队列、端点和凭据 | A 后台进程无法处理 B 的任务；无外部授权的副作用保持关闭 |
| 文件与证据 | 上传、临时文件、私有音频、截图、日志和报告按任务/验收批次保存 | 无同名覆盖；报告能定位本次实际产物 |

同一台 MySQL/PostgreSQL 服务可以承载多个专属测试库，前提是账号与连接明确隔离，并接受共享资源故障这一限制。环境隔离主要解决日常开发互相干扰，不是对拥有本机全盘权限的 Agent 的安全沙箱；数据库服务器故障、磁盘耗尽等仍可影响多个任务。

现有业务 `*_ENABLED` 开关只控制运行装配，不能推断为 Maven 编译隔离。每个工作树中的其他模块来自选定基线，因此另一工作树刚引入的编译错误不会传入；如果基线本身已坏，则先恢复可用基线再继续。

## 4. 启动工具的改造范围

在现有启动脚本基础上实现任务参数，而不是要求用户手工记忆一组命令。以下是拟定接口，尚未实现：

- 显式指定任务 ID、工作树路径、配置引用、后端端口、前端端口、前端主机名和运行目录。
- 为本次构建创建不可变运行产物副本，例如任务运行目录下按构建 ID 保存 JAR。运行进程使用该副本，避免后续 Maven 打包覆盖正在运行的 JAR。
- 启动前检查端口、数据库目标、Redis 目标和当前目录；缺少必要配置立即失败，禁止自动连接公共环境作为回退。
- 为任务记录 PID、启动时间、绝对产物路径、哈希及端口。停止前重新核对进程身份；只查端口或只记 PID 不足以防止误停其他任务。
- 前端端口占用时明确失败；HTTP 与 WebSocket 代理从同一任务配置读取，不能静默换端口或回退 8081。
- 输出可核对的任务身份与版本；身份查询只包含任务 ID、构建 ID 等非秘密信息，不返回密码、连接串或密钥。
- 创建新配置时从已核查的非秘密模板开始，通过既有凭据管理引用秘密；不批量复制原 `.env`，不把新环境自动连向现有业务库。

任务运行记录是机器配置和进程事实，不新增一套按会话划分的业务文档。功能规格、任务状态和验收证据继续归属各 Feature。

## 5. 内置浏览器及逐功能验收

默认继续使用 Codex 内置浏览器。每个任务使用自己持有的标签页句柄和专属入口，不操作其他任务页面。不假定多个标签页或多个 Codex 任务天然隔离 Cookie、登录态和存储。

采用任务专属主机名作为首选入口，如 `task-a.localhost` 与 `task-b.localhost`。实施时验证本机解析、Vite 主机白名单、代理、认证回调与实际 Cookie 范围；Cookie 限定在本任务主机，不设置跨任务父域。仅将 `127.0.0.1:15173` 改成 `127.0.0.1:15174` 不能隔离 Cookie。任务主机方案不适用时，应验证可用的独立浏览器上下文；若工具不能提供，则将有登录态冲突的验收串行处理，不宣称已隔离。

每次完成一个功能，就验收该功能和必要关联影响。流程沿用用户级 `C:\Users\admin\.codex\specs\core\evidence.md`，此处仅规定环境绑定：

1. 验收前展示并保存逐项清单，UI 项截图状态初始化为“待截图”。
2. 清单记录任务、基线/未提交差异标识、实际构建、入口、服务身份和测试数据批次。
3. 验收期间固定前后端版本；需继续开发时，使用静态构建/独立验收目录，或在本任务内完成该轮验收后再修改，避免 HMR 改变待验页面。
4. 逐项执行，截图落盘并回读核对，记录预期、实际、结果与截图状态；每项状态的定义继承用户级正文。
5. 生成并打开检查 `verification-report.html`，最终按清单逐项说明。失败、阻塞也形成报告；不能只交链接或一句“全部通过”。
6. 若发现版本变化、路由串线、数据串用，保留已有证据，将受影响项记为 Blocked，恢复本任务环境后定向重验。

## 6. 现有混合修改如何过渡

现有目录先作为需保护的工作现场，不能直接清理成集成环境。Git 工作树创建不会自动拆分这 4013 条状态记录，也不会天然带上未提交的新目录。

| 顺序 | 动作 | 进入下一步的条件 |
|---|---|---|
| 1 | 确认迁移涉及的现有任务、共同文件和运行实例；协调一个明确的短暂停写窗口 | 相关写入者与范围明确；不能在文件持续变化时声称取得一致快照 |
| 2 | 保存可恢复的源码和文档快照，包含新增、修改、删除清单及内容哈希；配置只保留非秘密结构与引用 | 快照可核对、可恢复，覆盖未跟踪源码；不能仅以 Git HEAD 代替当前内容 |
| 3 | 区分已完成共享目录迁移、公共修复和各业务任务修改；不确定归属的共同变更留在待集成集合 | 不按目录名盲目拆分交叉修改，不全量提交混合状态 |
| 4 | 选择并验证一个包含必要工程结构的共同基线；对仍未提交的任务内容形成独立补丁/文件清单 | 明确哪些已纳入基线、哪些保留在原目录、哪些进入任务工作树；完成对应构建与最小冒烟 |
| 5 | 在 Git 写操作授权范围内建立两个试点 worktree，并接入前述启动配置 | 每个任务路径、分支/基线、服务和数据映射明确；迁移后的任务上下文指向新目录 |
| 6 | 执行下表隔离验收，再按任务逐批迁移 | 两任务隔离验证通过；原现场保留至迁移内容与恢复条件核对完成 |

迁移失败时停用本次新建且归属已核对的试点进程，保留工作树和证据供排查，继续使用保留的原现场；不自动删除工作树、不重置原分支。任务测试库失败只影响对应试点库，不能通过恢复快照覆盖现有业务数据库。

## 8. 规范落点及本次交付边界

方案实施并验证后，项目根 `AGENTS.md` 只增加并行任务的入口约束和本文链接：开发前核对工作树与环境；不得修改他人目录或替换他人服务；环境归属不明时先解决归属；共享变更进入集成回归。跨项目验收规则仍由用户级 evidence 正文维护，不复制整套规范。

本次新增本设计及共享导航链接，不修改启动脚本、业务源码、已有任务工作目录或服务。本次不执行暂存、提交、分支创建、合并、服务启停或数据库写入。实施下一阶段需要明确覆盖工作树/分支创建、原任务迁移协调、测试资源创建和试点服务的范围，遵循既有用户级授权规则。

## 9. 技术依据

- [Git worktree 官方文档](https://git-scm.com/docs/git-worktree)：工作树提供同一仓库的多个检出目录；不负责数据库和服务隔离。
- [Codex 工作树说明](https://learn.chatgpt.com/docs/environments/git-worktrees)：应用支持以工作树承载任务；现有混合修改仍需明确迁移范围。
- [RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)：Cookie 不按端口隔离，因此不能只依靠不同端口保证登录态独立。

## 目标与边界

当前活跃 Java 后端位于 `platform-backend/`，截图中的 `ruoyi-backend/` 却是上游基线；活跃 Web、桌面、小程序和 Python 工程散列于仓库根目录。用户要求按技术类型集中管理，且 `ruoyi-backend/` 成为唯一活跃 Java Maven 聚合根。

本次迁移只改变工程位置、受路径影响的配置和入口说明。四个业务 Java 模块仍依赖若依平台装配，`ruoyi-admin` 仍是统一 HTTP 服务入口；`aps-worker` 仍为独立 Java 求解进程。业务数据库、认证权限、公共 API 和前端产品行为不因目录迁移而改变。模块默认启用与关闭机制沿用[Java 业务模块统一装配](Java业务模块统一装配.md)，实际联机前置条件也以该文档为准。

## 目标目录与迁移映射

目标目录以[架构文档的工程视图](工程按技术类型归档架构.md#工程视图)为准。这里维护一次性迁移映射，后续新增工程按类型落位。

| 原路径 | 目标路径 | 语义与处理 |
|---|---|---|
| `platform-backend/` | `ruoyi-backend/` | 用现有活跃平台工程作为目标根内容，保留所有工作区修改；不得把两套同名模块逐文件覆盖。 |
| 原 `ruoyi-backend/` | 新 `ruoyi-backend/_reference/ruoyi-original/` | 整体保存上游原文、许可和历史 `ruoyi-ui/`；不纳入目标父 POM。 |
| `platform-backend/ruoyi-ui/` | `frontend/_reference/ruoyi-ui/` | 旧 UI 参考工程，保留原文；不是活跃 `admin-web`。 |
| `admin-web/` | `frontend/admin-web/` | 活跃共享管理端。 |
| `portal-web/` | `frontend/portal-web/` | 活跃面试门户。 |
| `aden-desktop/` | `frontend/desktop/aden-desktop/` | 活跃 Electron 桌面端。 |
| `packages/interview-contracts/` | `frontend/packages/interview-contracts/` | 前端共享 TypeScript 契约包；其消费者的相对路径须同步更新。 |
| `mobile/` | `miniapp/interview-mobile/` | 活跃面试小程序，目录更名仅表达项目归属。 |
| `ruoyi-app/` | `miniapp/_reference/ruoyi-app/` | 若依上游移动端参考工程。 |
| `ruoyi-vue3-frontend/` | `frontend/_reference/ruoyi-vue3-frontend/` | 若依上游 Vue 3 参考工程。 |
| `fashion-ai-runtime/` | `python/fashion-ai-runtime/` | 选品 Python Runtime。 |
| `aden-agent-runtime/` | `python/aden-agent-runtime/` | Aden Agent Runtime。 |
| `aden-runner/` | `python/aden-runner/` | Aden Runner。 |

`contracts/` 保存跨语言公共契约，`prototype/` 保存原型，`scripts/` 保存跨工程脚本，`文档/` 保存人读文档；这些共享资产不混入某一语言工程。仓库根 `pom.xml` 如仍引用已删除的 `backend/`，须在迁移中确认其消费者并移除其“活跃构建入口”含义；不得让它与 `ruoyi-backend/pom.xml` 形成两个互相矛盾的入口。缓存、`target/`、虚拟环境和其他生成物按各工程忽略规则处理，不作为源文件迁移成果。

## 实施顺序与相容性

1. 记录 `git status`、源目录清单、现有嵌套 Git 状态和当前关键文件内容，保存包含未提交修改的可恢复副本；不把 `HEAD` 当作未提交内容备份。
2. 先保存原 `ruoyi-backend/` 上游基线，再将活跃 `platform-backend/` 整体迁入目标根。处理重名文件时按来源和语义判定，不静默覆盖。
3. 按映射移动 Web、桌面、小程序、Python 和上游前端参考工程；逐个检查项目内部相对路径、锁文件和资源引用。
4. 更新 Maven、启动脚本、CI、根级脚本、前端代理、TypeScript 包引用、开发容器/IDE 配置和文档入口。只改路径；端口、API 路由、鉴权和业务开关维持既有语义。
5. 对所有旧路径做定向搜索，区分历史记录与现行配置；更新现行入链，保留历史原文及本表映射。
6. 执行下方验证，将每项命令、预期、实际、结果和限制记录到跨项目[开发记录](../开发记录/README.md)中的本次迁移记录。验证通过后才删除兼容入口或迁移临时副本。

运行顺序仍为准备所需数据库和 schema、启动 `ruoyi-admin`，再按需要启动独立前端、Python Runtime 与 APS Worker。目录集中不自动合并进程，也不允许把 Python 运行时或 APS 求解任务隐式装配进若依 JVM。构建脚本、容器挂载、环境变量、CWD 和相对路径对目录调整敏感，必须按消费者逐一核对。

## 验证与停止条件

| 范围 | 最低验证 | 失败时处理 |
|---|---|---|
| Java | 在新 `ruoyi-backend/` 运行 `mvn -pl ruoyi-admin -am -DskipTests compile` 及受路径影响的定向测试；检查八个 APS 子模块和四业务模块进入 reactor。 | 停止把新根目录称为可用入口，修正 POM/脚本后重验。标准 package 若受现存进程占用，应如实记录，不停止用户进程。 |
| Web/桌面/小程序 | 在每个活跃工程运行其现有类型检查、测试或构建命令，核查开发代理和共享包解析。 | 定位具体路径消费者，避免用文件存在代替构建结果。 |
| Python | 在各项目环境中执行其已有轻量导入或定向测试，检查锁文件与相对文件加载。 | 保留依赖环境和旧路径恢复能力，避免默认安装或调用真实 Provider。 |
| 文档与脚本 | 执行 `scripts/check-docs.ps1`、相对链接检查、旧路径搜索和 `git diff --check`；手工审查历史与当前路径的语义。 | 将已有失败和本次新增失败分开记录。 |
| 联机启动 | 只在已准备隔离数据库、Redis 和必要配置时验证一个 `ruoyi-admin` 承载四组 HTTP API，APS Worker 独立。 | 环境不满足则记为未运行，不能据编译通过宣称联机可用。 |

若发现内容丢失、重名覆盖、无法恢复的路径消费者、意外数据库写入或公共接口变化，立即停止后续迁移。恢复时使用迁移前含未提交内容的副本按本表逆向还原目录，恢复受影响的现行路径引用与脚本，再运行迁移前可用的定向构建；不得仅依赖 Git 回退。未获得用户验收前，验证结果不能写成用户已接受。
